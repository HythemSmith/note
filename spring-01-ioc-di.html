1. Vấn đề code truyền thống — Phân tích sâu

Trước khi có Spring, code Java thuần thường trông như thế này:

public class OrderService {
    private PaymentGateway gateway;
    private EmailService emailService;
    private OrderRepository orderRepo;

    public OrderService() {
        this.gateway = new VnPayGateway();
        this.emailService = new EmailService();
        this.orderRepo = new OrderRepository();
    }

    public void createOrder(Order o) {
        orderRepo.save(o);
        gateway.pay(o.getTotal());
        emailService.sendConfirmation(o);
    }
}

🔬 Phân tích chi tiết 4 vấn đề

Vấn đề 1: Tight Coupling — Đo lường được

Coupling (độ phụ thuộc) đo mức độ class A phụ thuộc vào class B. Càng phụ thuộc → càng khó thay đổi.

Trong code trên:

  • OrderService phụ thuộc trực tiếp vào VnPayGateway — không phải qua interface.
  • Muốn đổi sang MoMo → sửa dòng new VnPayGateway() → rebuild → deploy.
  • Nếu VnPayGateway có constructor phức tạp → OrderService phải biết hết config của nó.
Bạn xây nhà và tự đúc gạch. Muốn đổi gạch đỏ sang gạch xám → phải đập cả bức tường. Nếu gạch được giao từ nhà máy (interface), bạn chỉ cần gọi nhà máy khác.

Vấn đề 2: Không testable — Root cause

Khi viết unit test cho OrderService:

@Test
void testCreateOrder() {
    OrderService svc = new OrderService();  // ← Bên trong new VnPayGateway
    svc.createOrder(new Order());
    // → VNPay API bị gọi thật!
    // → Email bị gửi thật!
}

Không thể test độc lập vì OrderService tự tạo dependency. Muốn mock, phải sửa code production — điều không nên.

Vấn đề 3: Transitive dependency — Chuỗi không dừng

Dependency không chỉ 1 tầng. Nó lan ra:

OrderService ├── VnPayGateway │ └── HttpClient │ └── HttpClientConfig │ └── Environment (đọc env var) │ ├── EmailService │ └── JavaMailSender │ └── SmtpConfig │ └── PropertySource │ └── OrderRepository └── EntityManager └── DataSource └── ConnectionPool └── JdbcUrl + credentials

Code khởi động app phải new cả cây dependency:

public static void main(String[] args) {
    // ... 10 dòng cho VnPay
    HttpClientConfig http = new HttpClientConfig(env.get("VNP_URL"));
    HttpClient client = new HttpClient(http);
    PaymentGateway gateway = new VnPayGateway(client, env.get("VNP_KEY"));
    
    // ... 10 dòng cho Email
    SmtpConfig smtp = new SmtpConfig(env.get("SMTP_HOST"), 
                                     Integer.parseInt(env.get("SMTP_PORT")));
    JavaMailSender sender = new JavaMailSender(smtp);
    EmailService email = new EmailService(sender);
    
    // ... 10 dòng cho Repo
    DataSource ds = new HikariDataSource(env.get("DB_URL"), 
                                          env.get("DB_USER"),
                                          env.get("DB_PASS"));
    EntityManager em = ds.createEntityManager();
    OrderRepository repo = new OrderRepository(em);
    
    // ... cuối cùng mới có OrderService
    OrderService svc = new OrderService(gateway, email, repo);
    
    // Và 100 dòng nữa cho 20 service khác...
}

Vấn đề 4: Lifecycle không ai quản lý — Bug resource leak

Giả sử có 5 service — mỗi cái new DataSource() riêng:

public class UserService {
    private DataSource ds = new HikariDataSource(config);  // 10 connections
}

public class OrderService {
    private DataSource ds = new HikariDataSource(config);  // 10 connections khác!
}

public class ProductService {
    private DataSource ds = new HikariDataSource(config);  // 10 connections khác!
}

Kết quả: 30 connections mở → DB có thể chịu không nổi → TooManyConnectionsException.

Không ai gọi ds.close() khi app shutdown → connections treo lơ lửng → DB lock.

Liên hệ SOLID — DIP

Code trên vi phạm Dependency Inversion Principle (D trong SOLID):

DIP: Module cấp cao không nên phụ thuộc module cấp thấp — cả hai nên phụ thuộc abstraction.
→ OrderService (cao) phụ thuộc VnPayGateway (thấp) — vi phạm.
→ Nên phụ thuộc PaymentGateway (interface).
Câu hỏi: "Code truyền thống có vấn đề gì — kể tên 4 vấn đề?"
Trả lời gọn: Tight coupling, không testable, transitive dependency chain, lifecycle không ai quản lý. Liên hệ DIP trong SOLID.

2. IoC — Hollywood Principle

IoC (Inversion of Control) = "Đảo ngược quyền điều khiển".

Nguyên tắc vàng gọi là Hollywood Principle:

"Don't call us, we'll call you" — Đừng gọi chúng tôi, chúng tôi sẽ gọi bạn.

Nghĩa là: thay vì code của bạn chủ động gọi framework, framework chủ động gọi code của bạn.

Phân tích trước / sau IoC

Không có IoC — Bạn gọi framework
// Bạn điều khiển:
public static void main(String[] args) {
    // 1. Bạn chọn tạo gì
    PaymentGateway gw = new VnPayGateway();
    
    // 2. Bạn chọn đưa vào đâu
    OrderService svc = new OrderService(gw);
    
    // 3. Bạn gọi method
    svc.createOrder(order);
}
// → Bạn là người chủ động
Có IoC — Framework gọi bạn
// Spring điều khiển:
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        // 1. Spring tự scan bean
        // 2. Spring tự tạo + inject
        // 3. Spring gọi method khi có request
        SpringApplication.run(App.class, args);
    }
}
// → Spring là người chủ động

4 loại IoC phổ biến

Loại IoC Cơ chế Ví dụ Spring dùng?
DI (Dependency Injection) Inject dependency vào object Spring, Guice ✅ Chính
Service Locator Lookup service từ registry JNDI, EJB ❌ (anti-pattern)
Template Method Framework gọi method override JdbcTemplate, JUnit ✅ Có
Event-driven Framework phát event Spring EventListener ✅ Có

Tại sao Spring chọn DI là chính?

  • Explicit dependency: nhìn constructor biết ngay cần gì.
  • Type-safe: compiler check được.
  • Testable: gọi constructor với mock là xong.
  • Immutable-friendly: field final được.

IoC Container là gì?

Container = cái hộp quản lý toàn bộ bean. Nó biết:

  • Bean nào tồn tại (từ BeanDefinition).
  • Bean nào cần bean nào (dependency graph).
  • Thứ tự tạo bean.
  • Vòng đời từng bean.
┌──────────────────────────────────────────────────────┐ │ APPLICATION CONTEXT (IoC Container) │ │ │ │ BeanRegistry (Map) │ │ ┌────────────────────────────────────────────────┐ │ │ │ "orderService" → OrderService instance │ │ │ │ "userRepository" → UserRepository instance │ │ │ │ "objectMapper" → ObjectMapper instance │ │ │ │ "dataSource" → HikariDataSource instance │ │ │ │ ... (hàng trăm bean khác) │ │ │ └────────────────────────────────────────────────┘ │ │ │ │ Metadata: │ │ - BeanDefinition của từng bean │ │ - Singleton cache │ │ - Lifecycle callbacks │ │ - Environment (properties, profiles) │ └──────────────────────────────────────────────────────┘
Câu hỏi: "IoC khác DI thế nào?"
Trả lời: IoC là nguyên lý (đảo ngược điều khiển), DI là cách thực hiện cụ thể. Spring chọn DI làm cơ chế chính vì nó explicit, type-safe, testable. Ngoài DI, Spring còn hỗ trợ Template Method (JdbcTemplate) và Event-driven (ApplicationEvent).

3. DI — 3 cách inject chi tiết

DI (Dependency Injection) = framework "tiêm" dependency vào object, thay vì object tự tạo.

① Constructor Injection — Phân tích sâu

@Service
public class OrderService {
    private final PaymentGateway gateway;
    private final EmailService email;
    private final OrderRepository repo;

    public OrderService(PaymentGateway gateway,
                        EmailService email,
                        OrderRepository repo) {
        this.gateway = gateway;
        this.email = email;
        this.repo = repo;
    }
}

Tại sao tốt — Phân tích ở mức bytecode/JVM

  1. Field final: JVM đảm bảo field final được gán đúng 1 lần trong constructor. Sau đó không thể thay đổi. → Thread-safe tự nhiên.
  2. Fail-fast: Nếu Spring không tìm thấy bean PaymentGateway → nó ném exception ngay lúc khởi động, không phải lúc có request. Bạn biết lỗi trước khi deploy.
  3. Không cần reflection để test: gọi new OrderService(mockGateway, mockEmail, mockRepo) → xong. Không cần Spring, không cần ReflectionTestUtils.
  4. Circular dependency phát hiện sớm: Nếu A cần B và B cần A qua constructor → Spring báo lỗi ngay. Không bị "che giấu" như field injection.
  5. Dependency rõ ràng: đọc constructor biết ngay class cần gì. Không phải đọc hết field.
Đào sâu — tại sao field final lại thread-safe? Trong JMM (Java Memory Model), field final được đảm bảo visible ngay sau khi constructor hoàn thành — không cần synchronize. Điều này quan trọng cho singleton bean bị nhiều thread dùng chung.

Với Lombok — Code gọn hơn

@Service
@RequiredArgsConstructor   // ← sinh constructor cho mọi field final
public class OrderService {
    private final PaymentGateway gateway;
    private final EmailService email;
    private final OrderRepository repo;
    // Không cần viết constructor tay
}
Lombok pitfall: Nếu bạn dùng @Qualifier trên field, Lombok không tự động copy sang constructor parameter. Cần config: 
// lombok.config
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier

② Setter Injection — Khi nào dùng?

@Service
public class OrderService {
    private PaymentGateway gateway;

    @Autowired
    public void setGateway(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

Ưu điểm:

  • Cho phép thay đổi dependency sau khi tạo.
  • Có thể tạo object trước, inject sau.
  • Dependency optional — nếu không inject, vẫn chạy được (với null check).

Nhược điểm:

  • Object không đảm bảo "ready" ngay sau constructor.
  • Không phải final → mutable → không thread-safe.

Khi nào dùng: dependency optional — ví dụ MetricsCollector có thể có hoặc không.

③ Field Injection — Tại sao tệ?

@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;   // ← không final
}

Nhìn gọn — nhưng có 5 vấn đề:

  1. Không final → mutable → không thread-safe.
  2. Không testable trực tiếp: Test phải dùng ReflectionTestUtils.setField() — không phải cách sạch.
  3. Không phát hiện circular dependency sớm: Spring có thể "giải quyết" bằng early reference — che giấu vấn đề thiết kế.
  4. Không rõ dependency: đọc code không thấy ngay class cần gì.
  5. Vi phạm Single Responsibility dễ hơn: vì không cần khai báo constructor, dễ có class 20 field injection mà không thấy "nặng".
Đào sâu — tại sao field injection được ưa chuộng "sai"? Vì code gọn, dễ viết. Nhưng gọn không có nghĩa là tốt. Spring team khuyến nghị constructor injection từ Spring 4.3. IntelliJ có inspection cảnh báo field injection.

So sánh tổng hợp 3 cách

Tiêu chí Constructor Setter Field
Immutable ✅ final ❌ ❌
Fail-fast ✅ ❌ ❌
Test dễ ✅ ✅ ❌ reflection
Circular detect ✅ sớm ❌ ❌
Optional dep ❌ ✅ ⚠️ required=false
Code dài Dài (trừ Lombok) Vừa Ngắn
Khuyến nghị ✅ Mặc định ⚠️ Optional ❌ Tránh

Các annotation inject

Annotation Chuẩn Hành vi
@Autowired Spring Inject theo type, có required=false
@Inject JSR-330 (Java EE) Tương đương @Autowired, không có required
@Resource JSR-250 (Java EE) Inject theo name trước, fallback theo type
@Qualifier Spring Chọn bean cụ thể — đi kèm với @Autowired
Câu hỏi: "Constructor injection tốt hơn field injection chỗ nào?"
Trả lời: 5 điểm — field final (immutable, thread-safe), fail-fast (lỗi ngay lúc startup), test dễ (không cần reflection), circular dependency phát hiện sớm, dependency rõ ràng. Ngoài ra Spring khuyến nghị constructor injection từ 4.3.

4. Khai báo bean — @Component vs @Bean chi tiết

Cách 1: @Component — trên class của bạn

@Service
public class OrderService {
    // Spring scan → tạo bean → đăng ký vào container
}

Các stereotype annotation

Annotation Ngữ nghĩa Xử lý đặc biệt
@Component Bean chung, không rõ tầng Không
@Service Tầng business Chỉ semantic
@Repository Tầng DAO Exception translation — dịch SQLException → DataAccessException
@Controller MVC controller Được DispatcherServlet detect
@RestController REST controller @Controller + @ResponseBody
@Configuration Class cấu hình CGLIB proxy cho @Bean method
Đào sâu — @Repository làm gì đặc biệt? Spring wrap bean bằng PersistenceExceptionTranslationPostProcessor. Khi method ném SQLException, proxy bắt và dịch thành DataAccessException (unchecked). Nhờ đó bạn bắt DuplicateKeyException thay vì phải parse SQLState của từng DB.

Cách 2: @Bean — trên method

@Configuration
public class AppConfig {

    @Bean
    public ObjectMapper objectMapper() {
        ObjectMapper om = new ObjectMapper();
        om.registerModule(new JavaTimeModule());
        om.setSerializationInclusion(JsonInclude.Include.NON_NULL);
        return om;
    }
}

@Bean có những thuộc tính gì?

@Bean(
    name = {"myBean", "aliasBean"},    // tên bean (mặc định = tên method)
    initMethod = "init",                // gọi sau khi tạo
    destroyMethod = "cleanup"           // gọi trước khi hủy
)
public MyBean myBean() { ... }

@Configuration(proxyBeanMethods) — Chi tiết

Mặc định @Configuration dùng CGLIB proxy để đảm bảo @Bean method trả về cùng bean khi gọi nội bộ:

@Configuration
public class AppConfig {

    @Bean
    public ObjectMapper om() {
        System.out.println("Tạo OM");
        return new ObjectMapper();
    }

    @Bean
    public RestTemplate rt() {
        ObjectMapper mapper = om();   // ← gọi qua proxy → trả về bean cũ
        return new RestTemplate();
    }
}

Log khi khởi động: "Tạo OM" chỉ in 1 lần — vì proxy cache.

@Component + @Bean method
@Component                        // ← KHÔNG có proxy
public class AppConfig {
    @Bean
    public ObjectMapper om() {
        System.out.println("Tạo OM");
        return new ObjectMapper();
    }
    
    @Bean
    public RestTemplate rt() {
        om();  // ← GỌI THẲNG → tạo mới
        return new RestTemplate();
    }
}
// → "Tạo OM" in 2 lần → 2 object khác nhau
@Configuration + @Bean method
@Configuration                    // ← CÓ proxy
public class AppConfig {
    @Bean
    public ObjectMapper om() {
        System.out.println("Tạo OM");
        return new ObjectMapper();
    }
    
    @Bean
    public RestTemplate rt() {
        om();  // ← qua proxy → trả bean cũ
        return new RestTemplate();
    }
}
// → "Tạo OM" in 1 lần → cùng 1 object

proxyBeanMethods = false — Khi nào dùng?

@Configuration(proxyBeanMethods = false)
public class AppConfig {
    // Không có CGLIB proxy
    // Startup nhanh hơn
    // NHƯNG: gọi @Bean method nội bộ sẽ tạo mới
}

Spring Boot 2+ dùng cách này cho auto-config — vì các auto-config class không gọi nhau nội bộ, không cần proxy → startup nhanh hơn nhiều.

Nếu dùng proxyBeanMethods = false mà vẫn muốn gọi @Bean method khác → dùng parameter injection thay vì gọi trực tiếp: 
@Bean
public RestTemplate rt(ObjectMapper om) {   // ← Spring inject
    return new RestTemplate();
}

So sánh @Component vs @Bean

@Component @Bean
Đặt ở Class Method
Ai tạo instance Spring (qua constructor) Bạn (trong method)
Dùng cho Class của bạn Class thư viện, cấu hình phức tạp
Auto scan ✅ ❌ (phải trong @Configuration)
Conditional @Conditional trên class @Conditional trên method
Câu hỏi: "@Component vs @Bean — khi nào dùng cái nào?"
Trả lời: Class của mình → @Component/@Service. Class thư viện (Jackson, Kafka...) → @Bean. Khi cần cấu hình phức tạp trước khi tạo → @Bean. Khi cần conditional → @Bean dễ hơn.

5. ComponentScan chi tiết

@ComponentScan = cơ chế Spring scan package để tìm bean.

Vị trí mặc định

@SpringBootApplication   // ← bao gồm @ComponentScan
public class Application {
    public static void main(String[] args) { ... }
}

Mặc định: scan package chứa class Application và tất cả sub-package.

com.example ├── Application.java ← @SpringBootApplication ở đây │ ├── controller/ ← ĐƯỢC SCAN ✅ │ └── UserController.java ├── service/ ← ĐƯỢC SCAN ✅ │ └── UserService.java └── repository/ ← ĐƯỢC SCAN ✅ └── UserRepository.java com.other ← KHÔNG ĐƯỢC SCAN ❌ └── OtherService.java
Nếu class Application ở package com.example.app → chỉ scan com.example.app. Các class trong com.example.service sẽ không được scan → lỗi NoSuchBeanDefinitionException.

Các thuộc tính của @ComponentScan

1. basePackages — scan package khác

@ComponentScan(basePackages = {"com.example.core", "com.example.api"})

2. basePackageClasses — type-safe

@ComponentScan(basePackageClasses = {UserService.class, OrderService.class})

→ Scan package chứa 2 class này. Ưu điểm: không dùng string (tránh typo).

3. includeFilters — thêm class

@ComponentScan(
    includeFilters = @ComponentScan.Filter(
        type = FilterType.REGEX,
        pattern = ".*Service"
    )
)

4. excludeFilters — loại class

@ComponentScan(
    excludeFilters = @ComponentScan.Filter(
        type = FilterType.ANNOTATION,
        classes = Deprecated.class
    )
)

FilterType

FilterTypeLọc theo
ANNOTATIONAnnotation có trên class
ASSIGNABLE_TYPEKế thừa / implement
ASPECTJAspectJ expression
REGEXRegex class name
CUSTOMTypeFilter tự định nghĩa

Tạo custom stereotype annotation

Ví dụ — chỉ scan class được đánh dấu riêng:

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component                          // ← meta-annotation
public @interface IntegrationAdapter {
}

// Dùng:
@IntegrationAdapter                 // ← tương đương @Component
public class StripeAdapter { ... }
Câu hỏi: "Nếu class @Service không được scan thì sao?"
Trả lời: Spring không tạo bean → khi inject vào chỗ khác sẽ báo NoSuchBeanDefinitionException. Fix: đặt class trong package được scan, hoặc mở rộng basePackages, hoặc đăng ký thủ công qua @Bean.

6. Resolve dependency — Thuật toán chi tiết

Thuật toán resolve đầy đủ

Khi Spring cần inject bean type T vào điểm inject: 1. Tìm tất cả bean có type assignable to T │ (bao gồm subclass, implementation) │ ├─ Nếu 0 bean: │ └─ Nếu required=true → NoSuchBeanDefinitionException │ Nếu required=false → inject null │ ├─ Nếu 1 bean → CHỌN │ └─ Nếu > 1 bean → tiếp bước 2 2. Lọc theo @Primary │ └─ Nếu có đúng 1 bean @Primary → CHỌN 3. Lọc theo @Qualifier │ └─ Nếu có @Qualifier(name) → match bean name → CHỌN 4. Lọc theo tên field/parameter │ └─ Nếu tên field/param khớp bean name → CHỌN 5. Không resolve được │ └─ NoUniqueBeanDefinitionException

Các exception cụ thể

Exception Khi nào
NoSuchBeanDefinitionException Không tìm thấy bean nào cùng type
NoUniqueBeanDefinitionException Có nhiều bean cùng type, không phân biệt được
BeanCurrentlyInCreationException Circular dependency
UnsatisfiedDependencyException Wrap các lỗi trên khi resolve constructor

Ví dụ — Nhiều bean cùng type

public interface PaymentGateway { void pay(double amount); }

@Component("vnpay")
public class VnPayGateway implements PaymentGateway { }

@Component("momo")
public class MomoGateway implements PaymentGateway { }

@Component("stripe")
public class StripeGateway implements PaymentGateway { }

Trường hợp 1: Không có @Primary, không có @Qualifier

@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;   // ← LỖI
}

→ NoUniqueBeanDefinitionException: expected single matching bean but found 3.

Trường hợp 2: Có @Primary

@Component("momo")
@Primary
public class MomoGateway implements PaymentGateway { }

→ Spring chọn MomoGateway làm mặc định.

Trường hợp 3: Dùng @Qualifier

@Service
public class OrderService {
    @Autowired
    @Qualifier("vnpay")               // ← chọn chính xác
    private PaymentGateway gateway;
}

Trường hợp 4: Fallback theo tên field/param

@Service
public class OrderService {
    @Autowired
    private PaymentGateway vnpay;   // ← tên field khớp bean name → chọn vnpay
}
Fallback theo tên field rất dễ gây bug khi refactor: đổi tên field → tự nhiên đổi bean được inject. Nên dùng @Qualifier rõ ràng.

@Qualifier trên field vs constructor param — Pitfall

@Service
@RequiredArgsConstructor            // ← Lombok sinh constructor
public class OrderService {
    @Qualifier("vnpay")             // ← Đặt ở field
    private final PaymentGateway gateway;
}

Câu hỏi: @Qualifier này có tác dụng không?

Trả lời: Không, nếu không config Lombok. Vì Spring resolve qua constructor parameter — mà Lombok không copy @Qualifier sang parameter.

Cách fix 1 — viết constructor tay:

@Service
public class OrderService {
    private final PaymentGateway gateway;

    public OrderService(@Qualifier("vnpay") PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

Cách fix 2 — cấu hình Lombok:

// lombok.config
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier

Custom qualifier annotation — Type-safe

@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier
public @interface VnPay { }

@Component
@VnPay
public class VnPayGateway implements PaymentGateway { }

@Service
public class OrderService {
    @Autowired
    @VnPay                              // ← type-safe, không string
    private PaymentGateway gateway;
}

Ưu điểm: không dùng string → compiler check được, tránh typo.

Câu hỏi: "Spring resolve dependency như thế nào khi có nhiều bean cùng type?"
Trả lời: Ưu tiên @Primary → @Qualifier → fallback theo tên field/param. Nếu vẫn không resolve → NoUniqueBeanDefinitionException.

7. Bean scope chi tiết

Singleton (mặc định)

@Service
public class UserService { }   // ← scope singleton mặc định

Đặc điểm:

  • 1 instance duy nhất cho mỗi IoC container.
  • Cache trong singletonObjects map.
  • Eager init — tạo lúc startup (khác với GoF Singleton lazy).
  • Bị nhiều thread dùng chung → phải thread-safe.
Đào sâu — Singleton (Spring) vs Singleton pattern (GoF)?
  • GoF Singleton: đảm bảo 1 instance per JVM, enforce bằng private constructor + static getInstance().
  • Spring Singleton: 1 instance per container. Không enforce bằng code — chỉ là scope. Bạn có thể có nhiều container → nhiều instance.

Prototype

@Service
@Scope("prototype")
public class ReportGenerator { }
  • Mỗi lần getBean() hoặc inject → tạo instance mới.
  • Spring không quản lý destroy — bạn phải tự cleanup.
  • Dùng khi bean có state riêng.
Prototype inject vào Singleton: Singleton tạo 1 lần → inject prototype lúc init → prototype chỉ có 1 instance thôi (không tạo mới mỗi request). Đây là bug thường gặp.

Cách fix: dùng ObjectProvider:

@Service
public class ReportService {
    private final ObjectProvider<ReportGenerator> genProvider;

    public void generate() {
        ReportGenerator gen = genProvider.getObject();   // ← tạo mới mỗi lần
        gen.run();
    }
}

Request scope

@Component
@RequestScope
public class RequestContext {
    private String userId;
    // Mỗi HTTP request có instance riêng, tự hủy sau request
}

Cơ chế đặc biệt: Spring dùng scoped proxy. Khi bạn inject RequestContext vào singleton bean, Spring inject một proxy. Proxy này delegate đến instance thật của request hiện tại (dùng RequestContextHolder).

Singleton bean (UserService) │ └── field: RequestContext (proxy) │ │ Mỗi khi gọi method ▼ Proxy lookup trong ThreadLocal │ ▼ Instance thật của request hiện tại

Session scope

@Component
@SessionScope
public class ShoppingCart {
    private List<Item> items = new ArrayList<>();
    // Sống theo session
}

Application / WebSocket scope

  • application: 1 instance per ServletContext. Hiếm dùng.
  • websocket: 1 instance per WebSocket session.

Bảng so sánh scope

Scope Số instance Vòng đời Proxy?
singleton 1 Cả app Không (trừ AOP)
prototype N Không quản lý destroy Không
request 1/request 1 HTTP request Có
session 1/session 1 HTTP session Có
application 1 ServletContext Có
Câu hỏi: "Singleton bean có thread-safe không? Prototype inject vào singleton có vấn đề gì?"
Trả lời: Singleton không tự thread-safe — nếu có mutable field thì phải tự bảo vệ. Prototype inject vào singleton → prototype chỉ tạo 1 lần, mất tính "new mỗi lần" — fix bằng ObjectProvider hoặc ApplicationContext.getBean().

8. ApplicationContext — Bên trong hoạt động thế nào?

BeanFactory vs ApplicationContext

BeanFactory ApplicationContext
Init mode Lazy — tạo bean khi getBean() Eager — tạo lúc startup
BeanPostProcessor Phải đăng ký thủ công Tự động
AOP Không Có
i18n (MessageSource) Không Có
Event publishing Không Có
Resource loading Không Có
Dùng khi App rất nhẹ (hiếm) Luôn luôn

Startup process — Chi tiết

1. Chọn ApplicationContext implementation │ (AnnotationConfigApplicationContext, ...) │ 2. Load BeanDefinitions │ ├─ Scan @Component │ ├─ Đọc @Bean method │ └─ Đọc XML (nếu có) │ → Đăng ký vào BeanDefinitionRegistry │ 3. Đăng ký BeanPostProcessor │ ├─ AutowiredAnnotationBeanPostProcessor │ ├─ CommonAnnotationBeanPostProcessor (@PostConstruct...) │ └─ PersistenceExceptionTranslationPostProcessor │ 5. Khởi tạo bean (theo thứ tự dependency) │ ├─ Instantiate (constructor) │ ├─ Populate (inject dependency) │ ├─ Aware interfaces (BeanNameAware...) │ ├─ BeanPostProcessor.postProcessBeforeInitialization │ ├─ @PostConstruct │ ├─ InitializingBean.afterPropertiesSet() │ ├─ init-method │ └─ BeanPostProcessor.postProcessAfterInitialization │ 6. Container sẵn sàng

BeanDefinition — Metadata

Khi Spring scan class, nó KHÔNG tạo object ngay. Nó tạo BeanDefinition — chứa metadata:

  • Class name.
  • Scope (singleton/prototype...).
  • Constructor arguments.
  • Properties.
  • Init method, destroy method.
  • Autowire mode.
  • Lazy init flag.
  • Depends-on beans.

BeanPostProcessor vs BeanFactoryPostProcessor

Đào sâu: @Autowired thực chất được xử lý bởi AutowiredAnnotationBeanPostProcessor. Nó implement BeanPostProcessor, hook vào postProcessProperties() để inject field/setter.
Câu hỏi: "BeanFactory khác ApplicationContext?"
Trả lời: BeanFactory là container cơ bản, lazy init. ApplicationContext kế thừa BeanFactory, thêm AOP, i18n, event, resource loading, và eager init (mặc định). Spring Boot luôn dùng ApplicationContext.

9. Circular Dependency + 3-level Cache

Circular Dependency là gì?

@Service
public class AService {
    private final BService b;
    public AService(BService b) { this.b = b; }
}

@Service
public class BService {
    private final AService a;
    public BService(AService a) { this.a = a; }
}

A cần B, B cần A → vòng lặp không giải được.

Tại sao constructor injection KHÔNG giải được?

Tạo AService │ ├─ Cần BService │ │ │ ├─ Cần AService │ │ │ │ │ └─ Cần BService ← VÒNG LẶP │ │ │ └─ LỖI: BeanCurrentlyInCreationException │ └─ Không tạo được

Constructor phải có đủ tham số MỚI tạo được object → không thể tạo trước.

Tại sao field injection "giải được"? — 3-level cache

Spring dùng 3 cấp cache để giải quyết:

Cache Type Chứa gì
Level 1 singletonObjects Bean đã hoàn chỉnh
Level 2 earlySingletonObjects Bean chưa inject xong — đã có reference
Level 3 singletonFactories Factory tạo proxy sớm

Quá trình tạo A và B

1. Tạo A: ├─ new AService() → instance A "trần" (chưa inject) ├─ Đưa factory A vào singletonFactories (level 3) └─ Cần inject B 2. Tạo B: ├─ new BService() → instance B "trần" ├─ Đưa factory B vào singletonFactories └─ Cần inject A 3. Cần A để inject vào B: ├─ Không có trong singletonObjects (level 1) ├─ Không có trong earlySingletonObjects (level 2) ├─ Có trong singletonFactories (level 3) ├─ Gọi factory → tạo early reference A ├─ Đưa A vào earlySingletonObjects (level 2) └─ Trả A (chưa inject xong) cho B 4. Inject A vào B → B hoàn chỉnh └─ Đưa B vào singletonObjects (level 1) 5. Inject B vào A → A hoàn chỉnh └─ Đưa A vào singletonObjects
Tại sao cần 3 cache, không phải 2? Level 3 (factory) cho phép trả về proxy thay vì reference — cần thiết khi A có AOP (ví dụ @Transactional). Proxy này sẽ được thay bằng object thật sau khi A hoàn chỉnh.

Tại sao constructor injection vẫn lỗi?

Vì không có "instance trần" để đưa vào cache. Constructor cần đủ tham số MỚI tạo được object. Không thể đưa "half-baked" object vào cache.

Cách fix circular dependency

❌ Cách sai — che giấu

  • Dùng field injection — Spring có thể giải nhưng đây là code smell.
  • Dùng @Lazy ở 1 đầu — chỉ che giấu vấn đề thiết kế.

✅ Cách đúng — Refactor

  • Tách logic chung ra class C thứ 3.
  • Dùng event nếu là publish/subscribe.
  • Đảo chiều 1 dependency — dùng interface.
Từ Spring Boot 2.6, circular dependency bị cấm mặc định — kể cả field injection. Phải set spring.main.allow-circular-references=true mới cho phép. Đây là khuyến khích refactor.
Câu hỏi: "Circular dependency — Spring giải quyết thế nào? Tại sao constructor không giải được?"
Trả lời: Spring dùng 3-level cache: singletonObjects (bean hoàn chỉnh), earlySingletonObjects (early ref), singletonFactories (factory tạo proxy). Constructor không giải được vì không thể tạo object trần — constructor cần đủ tham số mới chạy. Field injection giải được vì Spring tạo object trước, inject sau.

10. Self-injection — Proxy mechanism

Vấn đề

@Service
public class OrderService {

    public void createOrder(Order o) {
        this.processPayment(o);   // ← gọi method cùng class
    }

    @Transactional
    public void processPayment(Order o) {
        // Transaction KHÔNG chạy
    }
}

Tại sao không chạy?

@Transactional hoạt động qua proxy:

Khi gọi từ NGOÀI: Client → Proxy.beginTransaction() │ └─ RealObject.processPayment() │ └─ Proxy.commit() Khi gọi NỘI BỘ (this.processPayment()): Client → Proxy.createOrder() │ └─ RealObject.createOrder() │ └─ this.processPayment() ← gọi trực tiếp (không qua proxy → không transaction)

Cách fix

Cách 1: Tách class (tốt nhất)

@Service
public class PaymentService {
    @Transactional
    public void processPayment(Order o) { ... }
}

@Service
public class OrderService {
    private final PaymentService paymentService;

    public void createOrder(Order o) {
        paymentService.processPayment(o);   // ← qua proxy
    }
}

Cách 2: Self-injection

@Service
public class OrderService {
    @Autowired
    @Lazy                          // ← cần @Lazy để tránh circular
    private OrderService self;

    public void createOrder(Order o) {
        self.processPayment(o);    // ← qua proxy
    }

    @Transactional
    public void processPayment(Order o) { ... }
}

Cách 3: AopContext.currentProxy() (cũ)

@EnableAspectJAutoProxy(exposeProxy = true)

public void createOrder(Order o) {
    ((OrderService) AopContext.currentProxy()).processPayment(o);
}

Nhược điểm: code bẩn, khó test.

Câu hỏi: "Tại sao gọi method @Transactional trong cùng class lại không có transaction?"
Trả lời: Vì @Transactional hoạt động qua proxy. Gọi từ ngoài → qua proxy → có transaction. Gọi nội bộ (this.method()) → gọi trực tiếp real object → không qua proxy. Fix: tách class hoặc self-injection.

11. Conditional Bean — @Conditional

@Conditional cơ bản

@Configuration
public class AppConfig {

    @Bean
    @Conditional(OnWindowsCondition.class)
    public FileStorage windowsStorage() {
        return new WindowsFileStorage();
    }

    @Bean
    @Conditional(OnLinuxCondition.class)
    public FileStorage linuxStorage() {
        return new LinuxFileStorage();
    }
}

Các @Conditional có sẵn của Spring Boot

Annotation Điều kiện
@ConditionalOnClass Có class trong classpath
@ConditionalOnMissingClass Không có class trong classpath
@ConditionalOnBean Có bean trong container
@ConditionalOnMissingBean Không có bean trong container
@ConditionalOnProperty Property có giá trị cụ thể
@ConditionalOnWebApplication Là web app
@ConditionalOnNotWebApplication Không phải web app
@ConditionalOnResource Resource tồn tại
@ConditionalOnExpression SpEL expression true

Ví dụ thực tế — @ConditionalOnProperty

@Component
@ConditionalOnProperty(
    name = "payment.provider",
    havingValue = "vnpay",
    matchIfMissing = false        // nếu property không có → không tạo bean
)
public class VnPayGateway implements PaymentGateway { ... }
# application-prod.yml
payment.provider: vnpay

Kết quả: chỉ VnPayGateway bean được tạo khi property = "vnpay".

@ConditionalOnMissingBean — Override default bean

@Configuration
public class DefaultConfig {

    @Bean
    @ConditionalOnMissingBean                     // ← chỉ tạo nếu user chưa định nghĩa
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

User có thể override:

@Configuration
public class CustomConfig {

    @Bean
    public ObjectMapper objectMapper() {         // ← bean này được dùng
        ObjectMapper om = new ObjectMapper();
        om.registerModule(new JavaTimeModule());
        return om;
    }
}

→ Spring ưu tiên bean của user. Đây là cơ chế của Spring Boot auto-configuration.

Viết custom @Conditional

public class OnProductionCondition implements Condition {
    @Override
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        String profile = ctx.getEnvironment().getProperty("spring.profiles.active");
        return "prod".equals(profile);
    }
}

@Configuration
@Conditional(OnProductionCondition.class)
public class ProdConfig { ... }
Câu hỏi: "@ConditionalOnMissingBean dùng khi nào?"
Trả lời: Trong auto-configuration — tạo bean default chỉ khi user chưa định nghĩa. Cho phép user override. Đây là cách Spring Boot cho phép "custom hóa mặc định".

12. Collection Injection — Inject nhiều bean

Inject tất cả bean cùng type vào List

public interface PaymentGateway { void pay(double amount); }

@Component public class VnPayGateway implements PaymentGateway { }
@Component public class MomoGateway implements PaymentGateway { }
@Component public class StripeGateway implements PaymentGateway { }

@Service
public class PaymentService {
    private final List<PaymentGateway> gateways;   // ← inject TẤT CẢ

    public PaymentService(List<PaymentGateway> gateways) {
        this.gateways = gateways;   // [VnPay, Momo, Stripe]
    }
}

→ Spring inject tất cả bean cùng type vào List. Thứ tự theo @Order hoặc Ordered.

Inject vào Map

@Service
public class PaymentService {
    private final Map<String, PaymentGateway> gateways;
    // key = bean name, value = bean

    public void payWith(String provider, double amount) {
        PaymentGateway gw = gateways.get(provider);   // "vnpay" → VnPayGateway
        gw.pay(amount);
    }
}

→ Đây là Strategy pattern implement cực gọn trong Spring.

@Order để sắp xếp

@Component
@Order(1)
public class FirstFilter implements Filter { }

@Component
@Order(2)
public class SecondFilter implements Filter { }

→ Trong List, FirstFilter trước SecondFilter.

Inject Optional

@Service
public class PaymentService {
    private final Optional<MetricsCollector> metrics;

    public PaymentService(Optional<MetricsCollector> metrics) {
        this.metrics = metrics;
    }

    public void pay() {
        metrics.ifPresent(m -> m.record("payment"));
    }
}
Câu hỏi: "Làm sao implement Strategy pattern trong Spring?"
Trả lời: Inject Map<String, Strategy> — key = bean name, value = strategy. Spring tự inject tất cả bean cùng type. Rồi lookup theo name để chọn strategy.

13. Lazy Init — @Lazy chi tiết

@Lazy trên bean

@Service
@Lazy                             // ← tạo khi lần đầu được getBean()
public class HeavyService { }

Mặc định singleton → eager. @Lazy → tạo khi cần lần đầu.

@Lazy trên điểm inject

@Service
public class OrderService {
    @Autowired
    @Lazy                              // ← inject proxy, tạo khi gọi method
    private ExpensiveService expensive;
}

Spring inject proxy. Khi gọi method lần đầu → mới tạo bean thật.

@Lazy để fix circular dependency

@Service
public class AService {
    private final BService b;

    public AService(@Lazy BService b) {   // ← B tạo lazy
        this.b = b;
    }
}

→ Khi tạo A, không cần B ngay → phá vòng lặp.

@Lazy chỉ che giấu circular dependency — không sửa gốc vấn đề thiết kế. Chỉ dùng tạm khi không refactor được.

Global lazy init

# application.yml
spring:
  main:
    lazy-initialization: true

→ Tất cả bean lazy. Startup nhanh hơn nhưng lỗi chỉ xuất hiện lúc runtime — không khuyến nghị cho production.

Khi nào dùng @Lazy?

  • Bean rất nặng — chỉ cần khi có feature cụ thể.
  • Bean không dùng ở mọi request.
  • Test — skip init không cần thiết.
  • Break circular dependency (tạm).

14. Best Practices + Checklist

✅ Nên làm

  • Constructor injection — dùng final, dùng Lombok @RequiredArgsConstructor.
  • Bean stateless — không giữ mutable field trong singleton.
  • Program to interface — inject qua interface để dễ mock.
  • @Qualifier cụ thể — thay vì dựa vào @Primary.
  • Custom qualifier annotation — type-safe hơn string.
  • @ComponentScan basePackageClasses — thay vì string package.
  • @Configuration(proxyBeanMethods = false) khi không cần proxy.
  • @Conditional cho optional bean.
  • Tách class khi circular dependency — không dùng @Lazy che.

❌ Không nên

  • Field injection — khó test, mutable, che circular dependency.
  • @Autowired không cần thiết — constructor duy nhất đã tự động.
  • Bean có state — race condition.
  • Gọi @Transactional/@Cacheable nội bộ — self-invocation.
  • new cho class có DI — object không có dependency.
  • Dùng @Lazy tràn lan — che giấu vấn đề.
  • @Component thay @Configuration khi có @Bean method gọi nhau.
