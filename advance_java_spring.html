1. Design Patterns (Creational · Structural · Behavioral)

1. Design pattern là gì? Có mấy nhóm chính?

Design pattern là giải pháp tái sử dụng cho các vấn đề thiết kế phổ biến. Không phải code cụ thể mà là khuôn mẫu.

3 nhóm chính (GoF — Gang of Four):

  • Creational (Khởi tạo): Singleton, Factory Method, Abstract Factory, Builder, Prototype.
  • Structural (Cấu trúc): Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight.
  • Behavioral (Hành vi): Observer, Strategy, Template Method, Command, Iterator, State, Chain of Responsibility, Mediator, Visitor, Memento.
Phỏng vấn middle hay hỏi: "Bạn đã dùng pattern nào trong dự án thật?" — phải kể tên cụ thể + use case + lợi ích.
2. Singleton pattern — mục đích, cách implement an toàn, use case?

Mục đích: đảm bảo 1 class chỉ có duy nhất 1 instance trong toàn bộ JVM.

Cách implement an toàn (thread-safe, lazy, chống reflection + serialization):

public enum Singleton {
  INSTANCE;
  public void doWork() { ... }
}

Enum là cách an toàn nhất — JVM đảm bảo, chống reflection & serialization tự động.

Cách khác (double-checked locking):

public class Singleton {
  private static volatile Singleton instance;
  private Singleton() {}
  public static Singleton getInstance() {
    if (instance == null) {
      synchronized (Singleton.class) {
        if (instance == null) instance = new Singleton();
      }
    }
    return instance;
  }
}

Use case thực tế:

  • Spring bean scope singleton (mặc định) — mọi @Service, @Repository.
  • Logger factory, Configuration manager.
  • Connection pool (HikariCP).
  • Cache manager.
Nhấn mạnh: Singleton pattern (GoF) ≠ singleton scope (Spring). GoF là per-JVM; Spring là per-container.
3. Factory Method vs Abstract Factory?

Factory Method: 1 method tạo 1 loại object. Subclass quyết định concrete class.

interface PaymentFactory { Payment create(); }
class VnPayFactory implements PaymentFactory {
  public Payment create() { return new VnPayPayment(); }
}

Abstract Factory: 1 interface tạo họ object liên quan.

interface UIFactory {
  Button createButton();
  Checkbox createCheckbox();
}
class DarkUIFactory implements UIFactory { ... }
class LightUIFactory implements UIFactory { ... }

Khác biệt: Factory Method = 1 sản phẩm; Abstract Factory = nhiều sản phẩm liên quan, đảm bảo tương thích.

Use case Spring: BeanFactory / ApplicationContext chính là Abstract Factory.

4. Builder pattern — khi nào dùng?

Mục đích: xây dựng object phức tạp (nhiều tham số optional) theo từng bước. Tránh telescoping constructor (constructor dài).

User u = User.builder()
    .name("Alice")
    .email("a@b.com")
    .age(25)
    .build();

Khi dùng:

  • Object có > 4 tham số, nhiều cái optional.
  • Cần immutable object.
  • Ví dụ: HttpRequest.newBuilder(), StringBuilder (tương tự), Lombok @Builder.
Spring UriComponentsBuilder, WebClient.Builder, ResponseEntity.ok() đều là Builder.
5. Adapter pattern — ví dụ thực tế?

Mục đích: chuyển interface A thành interface B để 2 class không tương thích làm việc được với nhau.

Ví dụ phỏng vấn hay hỏi: có MediaPlayer và MediaPackage — MP3 implements MediaPlayer, còn VLC/MP4 implements MediaPackage. Muốn dùng MediaPackage như MediaPlayer → cần Adapter.

interface MediaPlayer { void play(String file); }

class MediaAdapter implements MediaPlayer {
  private MediaPackage pack;
  public MediaAdapter(MediaPackage pack) { this.pack = pack; }
  public void play(String file) { pack.playFile(file); }
}

Use case thực tế:

  • Tích hợp payment gateway (VNPay, MoMo, Stripe) — mỗi cái có API khác → adapter về interface chung.
  • Wrap thư viện bên thứ 3 (Jackson, Kafka client) thành interface của dự án.
  • Spring MVC HandlerAdapter — adapter giữa DispatcherServlet và controller.
6. Observer pattern — use case?

Mục đích: 1 object (Subject) thay đổi → thông báo cho nhiều object (Observer) đang lắng nghe.

interface Observer { void update(String msg); }

class Subject {
  private List<Observer> observers = new ArrayList<>();
  public void attach(Observer o) { observers.add(o); }
  public void notifyAll(String msg) {
    observers.forEach(o -> o.update(msg));
  }
}

Use case:

  • Event-driven: Spring ApplicationEventPublisher + @EventListener.
  • Kafka/RabbitMQ ở tầng hệ thống (pub/sub).
  • UI: button click listener.
  • Reactive programming: RxJava, Reactor.
7. Decorator pattern — khác Strategy chỗ nào?

Decorator: wrap object để thêm hành vi mà không đổi class gốc. Có thể wrap nhiều lớp.

InputStream is = new BufferedInputStream(
                    new FileInputStream("f.txt"));

Strategy: chọn 1 trong nhiều thuật toán tại runtime, không bọc.

sorter.setStrategy(new QuickSort());
sorter.sort(arr);

Khác biệt:

  • Decorator: thêm hành vi (composition, đệ quy wrap).
  • Strategy: thay hành vi (chọn implementation).

Use case Decorator: java.io.* (InputStream chain), Spring AOP, HTTP filter chain, Spring Security filter chain.

8. Strategy pattern — ví dụ? 
interface ShippingStrategy { double calc(Order o); }

@Component("fast") class FastShipping implements ShippingStrategy { ... }
@Component("cheap") class CheapShipping implements ShippingStrategy { ... }

@Service
public class OrderService {
  private final Map<String, ShippingStrategy> strategies;
  public OrderService(Map<String, ShippingStrategy> strategies) {
    this.strategies = strategies; // Spring inject toàn bộ bean theo name
  }
  public double ship(String type, Order o) {
    return strategies.get(type).calc(o);
  }
}

Use case: tính phí ship, thuế theo quốc gia, thuật toán nén file, sort, discount rule.

Spring inject Map<String, Strategy> rất tiện — key là bean name. Đây là pattern phổ biến trong dự án thực tế.
9. Facade, Proxy, Template Method?
  • Facade: cung cấp interface đơn giản che giấu hệ thống phức tạp. Ví dụ: JdbcTemplate che giấu connection/statement/resultset boilerplate.
  • Proxy: đại diện cho object khác để kiểm soát truy cập. Spring AOP dùng proxy để thêm @Transactional, @Cacheable. Java có java.lang.reflect.Proxy (JDK dynamic proxy) và CGLIB.
  • Template Method: định nghĩa skeleton của thuật toán, để subclass override 1 số bước. Ví dụ: JdbcTemplate.execute(), AbstractList.
// Template Method
public abstract class DataImporter {
  public final void importData() {  // template
    open();
    parse();
    save();
    close();
  }
  protected abstract void parse();
}
10. Chain of Responsibility — use case?

Mục đích: chuyển request qua 1 chuỗi handler, mỗi handler quyết định xử lý hoặc chuyển tiếp.

public interface Handler {
  void setNext(Handler h);
  Response handle(Request req);
}

Use case:

  • Spring Security Filter Chain — chain các filter (auth, csrf, cors...).
  • Servlet Filter chain.
  • Logging middleware (MdcFilter → AccessLog → RateLimit).
  • Validation chain, approval workflow.
11. Có pattern nào bạn ghét / thấy bị lạm dụng?

Câu hỏi "trap" — muốn xem bạn có chính kiến không.

Gợi ý trả lời:

  • Singleton bị lạm dụng: khó test, hidden dependency. Dùng DI thay thế.
  • Abstract Factory quá sớm: khi chưa có nhu cầu thực sự → over-engineer.
  • God Object / Manager class: không phải pattern nhưng là anti-pattern phổ biến — 1 class ôm quá nhiều trách nhiệm.
  • Service Locator: anti-pattern, thay bằng DI.
  • Anemic Domain Model: entity chỉ có getter/setter, business logic dồn hết vào service → mất OOP.

2. SOLID & Clean Code

12. SOLID là gì? Giải thích từng chữ?
  • S — Single Responsibility Principle: 1 class chỉ có 1 lý do để thay đổi. Ví dụ: tách UserRepository (DB) khỏi UserService (business) khỏi UserController (HTTP).
  • O — Open/Closed Principle: mở rộng được (kế thừa, interface) nhưng không sửa code cũ. Ví dụ: thêm ExportPDF không cần sửa ExportService — dùng interface Exporter.
  • L — Liskov Substitution Principle: class con phải thay thế được class cha mà không phá vỡ hành vi. Ví dụ: Square extends Rectangle là vi phạm LSP (setWidth làm thay đổi height).
  • I — Interface Segregation Principle: nhiều interface nhỏ > 1 interface lớn. Client không nên bị force implement method không dùng. Ví dụ: tách Printable, Scannable, Faxable thay vì MultiFunctionDevice.
  • D — Dependency Inversion Principle: phụ thuộc vào abstraction, không phụ thuộc vào concrete class. Đây là nền tảng của DI trong Spring.
// DIP
// ❌ Sai — service phụ thuộc concrete
class OrderService {
  private MySQLOrderRepo repo = new MySQLOrderRepo();
}

// ✅ Đúng — service phụ thuộc interface
class OrderService {
  private OrderRepository repo; // interface
  OrderService(OrderRepository repo) { this.repo = repo; }
}
Phỏng vấn hay hỏi: "Cho ví dụ vi phạm SOLID mà em từng gặp và cách sửa?" — nên có 1 ví dụ thật từ dự án.
13. DRY, KISS, YAGNI là gì?
  • DRY (Don't Repeat Yourself): tránh lặp logic. Nhưng cẩn thận — 2 đoạn code giống nhau vì lý do khác nhau thì không nên gộp (false DRY).
  • KISS (Keep It Simple, Stupid): giải pháp đơn giản nhất thường tốt nhất. Tránh over-engineer.
  • YAGNI (You Aren't Gonna Need It): đừng code tính năng "phòng khi cần" — chưa có yêu cầu thì đừng làm.

Cộng thêm: Boy Scout Rule — để code sạch hơn khi bạn rời đi so với khi đến.

14. Code smell là gì? Kể tên vài cái phổ biến?

Code smell: dấu hiệu code có vấn đề thiết kế (không phải bug).

  • Long method: method > 30–50 dòng.
  • Long parameter list: > 3–4 tham số → dùng DTO/Builder.
  • Duplicated code: copy-paste logic.
  • God class: 1 class làm quá nhiều việc (1000+ dòng).
  • Feature envy: method dùng field của class khác nhiều hơn class mình.
  • Primitive obsession: dùng String/int cho mọi thứ thay vì Value Object (Email, Money, PhoneNumber).
  • Shotgun surgery: 1 thay đổi nhỏ phải sửa nhiều file.
  • Magic number/string: hardcode 86400, "ACTIVE" → dùng constant hoặc enum.
15. Composition vs Inheritance — ưu tiên cái nào?

Nguyên tắc: "Favor composition over inheritance".

  • Inheritance: quan hệ "is-a", coupling chặt, khó thay đổi runtime.
  • Composition: quan hệ "has-a", linh hoạt, thay đổi runtime dễ.
// ❌ Inheritance
class Car extends Engine { }  // xe "là" động cơ? Sai

// ✅ Composition
class Car {
  private Engine engine;  // xe "có" động cơ
  Car(Engine e) { this.engine = e; }
}

Spring DI khuyến khích composition — inject dependency thay vì extend abstract class.

Nếu interviewer hỏi "tại sao Java không đa kế thừa class?" → vì diamond problem; và composition giải quyết vấn đề này tốt hơn.
16. Clean Code — những nguyên tắc bạn áp dụng?
  • Đặt tên rõ ràng: calculateMonthlyInterest() > calc().
  • Hàm ngắn, làm 1 việc: < 20 dòng, 1 mức abstraction.
  • Comment khi cần WHY, không phải WHAT: code nói "what", comment nói "why".
  • Tránh comment thừa: // tăng i lên 1 — vô nghĩa.
  • Format nhất quán: dùng formatter (Checkstyle, Spotless).
  • Xử lý lỗi tường minh: không catch (Exception e) {}.
  • Viết test: code không test = legacy code.
  • Nguyên tắc Boy Scout: để lại sạch hơn khi đi.

3. Database Normalization

17. Normalization là gì? Tại sao cần?

Normalization: quá trình tổ chức dữ liệu để giảm dư thừa và tăng tính toàn vẹn.

Mục đích:

  • Loại bỏ dữ liệu trùng lặp.
  • Tránh anomaly khi insert/update/delete.
  • Đảm bảo phụ thuộc logic hợp lý.

Nhược điểm: nhiều bảng → nhiều JOIN → query chậm hơn. Trong thực tế đôi khi phải denormalize (chấp nhận dư thừa) để tối ưu đọc.

18. 1NF là gì?

First Normal Form (1NF):

  • Mỗi cột chỉ chứa giá trị nguyên tử (atomic) — không list, không JSON array, không comma-separated.
  • Không có cột lặp lại (ví dụ phone1, phone2, phone3 → sai).
  • Mỗi row phải unique (có primary key).

Ví dụ vi phạm:

| id | name  | phones               |
| 1  | Alice | 0901,0902,0903       |  ❌

Chuẩn hóa: tách bảng user_phone(user_id, phone).

19. 2NF là gì?

Second Normal Form (2NF):

  • Đã đạt 1NF.
  • Không có phụ thuộc một phần (partial dependency) — mọi non-key attribute phụ thuộc toàn bộ composite primary key, không phải chỉ 1 phần.

Ví dụ vi phạm: bảng order_item(order_id, product_id, product_name, qty) — product_name chỉ phụ thuộc product_id, không phụ thuộc cả composite key (order_id, product_id).

Chuẩn hóa: tách product(product_id, product_name) khỏi order_item(order_id, product_id, qty).

20. 3NF là gì?

Third Normal Form (3NF):

  • Đã đạt 2NF.
  • Không có phụ thuộc bắc cầu (transitive dependency) — non-key attribute không phụ thuộc vào non-key attribute khác.

Ví dụ vi phạm: employee(emp_id, dept_id, dept_name, dept_manager) — dept_name và dept_manager phụ thuộc dept_id, mà dept_id là non-key → bắc cầu.

Chuẩn hóa: tách department(dept_id, dept_name, dept_manager).

Quy tắc nhớ: "Mọi non-key attribute phụ thuộc trực tiếp vào primary key, không qua trung gian".

21. BCNF là gì? Khác 3NF?

Boyce-Codd Normal Form (BCNF) = 3NF mạnh hơn.

Điều kiện: mọi determinant (vế trái của functional dependency) phải là super key.

Khác 3NF: 3NF cho phép non-key attribute là determinant (nếu nó là phần của candidate key); BCNF không cho phép.

Ví dụ vi phạm BCNF nhưng đạt 3NF: (student, course, teacher) — 1 teacher dạy 1 course, nhưng 1 course có nhiều teacher. Nếu key là (student, course), thì teacher → course nhưng teacher không phải super key → vi phạm BCNF.

Các cấp cao hơn: 4NF (loại multi-valued dependency), 5NF (join dependency).

Thực tế production thường dừng ở 3NF. BCNF chỉ dùng khi có yêu cầu chặt về integrity.
22. Denormalization là gì? Khi nào dùng?

Denormalization: cố ý thêm dư thừa để tăng tốc đọc.

Khi nào dùng:

  • Read-heavy system (báo cáo, dashboard).
  • JOIN quá nhiều bảng → chậm.
  • Data warehouse (OLAP) — khác OLTP.
  • Cache computed value: ví dụ lưu total_orders trong bảng user thay vì COUNT mỗi lần.

Đánh đổi: đọc nhanh nhưng ghi chậm hơn (phải update nhiều nơi), dễ mất đồng bộ.

4. Security nâng cao

23. XSS là gì? Cách prevent?

XSS (Cross-Site Scripting): attacker inject JavaScript vào trang, chạy trong browser của nạn nhân.

3 loại:

  • Stored XSS: script lưu trong DB (comment, profile) → hiển thị cho mọi user.
  • Reflected XSS: script trong URL param, phản chiếu ngay về response.
  • DOM-based XSS: script chạy ở client do JS xử lý DOM không an toàn.

Prevent:

  • Output encoding: escape HTML khi render (Thymeleaf, React tự động).
  • Content Security Policy (CSP): header chặn inline script.
  • HttpOnly cookie: JS không đọc được cookie.
  • Validate input: whitelist, không blacklist.
  • Không dùng innerHTML với dữ liệu user.
24. SQL Injection là gì? Cách prevent?

SQL Injection: attacker chèn SQL vào input → query thực thi lệnh độc hại.

// ❌ Vulnerable
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
// Nếu name = "' OR '1'='1" → trả về toàn bộ user

// ✅ Safe — PreparedStatement
String sql = "SELECT * FROM users WHERE name = ?";
ps.setString(1, name);

Prevent:

  • PreparedStatement / parameterized query (luôn dùng).
  • JPA/Hibernate: dùng JPQL với parameter (:name), tránh nối chuỗi.
  • Validate input: whitelist ký tự.
  • Least privilege: DB account chỉ có quyền cần thiết.
  • WAF: Web Application Firewall.
Native query trong JPA cũng có thể bị SQLi nếu dùng String.format — luôn dùng @Param và :param.
25. CSRF là gì? Khi nào cần bật/tắt?

CSRF (Cross-Site Request Forgery): attacker lừa browser user (đã login) gửi request không mong muốn.

Ví dụ: user đang login ngân hàng, vào trang evil.com có form ẩn POST đến /transfer. Browser tự đính cookie ngân hàng → giao dịch thành công.

Prevent:

  • CSRF token: server sinh token, client gửi kèm request, server verify.
  • SameSite cookie: SameSite=Strict/Lax chặn cookie cross-site.
  • Check Origin/Referer header.
  • Không dùng GET cho thao tác thay đổi.

Spring Security:

// Session-based auth: BẬT CSRF (default)
http.csrf(Customizer.withDefaults());

// REST API + JWT trong header: TẮT CSRF
http.csrf(AbstractHttpConfigurer::disable);

Lý do tắt với JWT: attacker không đọc được token từ domain khác → không tự đính được như cookie.

26. Stateful vs Stateless Authentication?

Stateful:

  • Server lưu session (in-memory, Redis).
  • Client gửi session ID qua cookie.
  • Ưu: revoke dễ, không lộ token mỗi request.
  • Nhược: scale khó (sticky session, share session store).

Stateless:

  • Không lưu state server-side. Client giữ token (JWT).
  • Server verify token mỗi request.
  • Ưu: scale ngang dễ, phù hợp microservices.
  • Nhược: revoke khó (phải blacklist hoặc token ngắn hạn + refresh token).

Chọn: monolith + web truyền thống → stateful. Microservices + mobile → stateless JWT.

27. SSO là gì? Implement thế nào trong microservices?

SSO (Single Sign-On): đăng nhập 1 lần, dùng được nhiều hệ thống.

Chuẩn phổ biến: OAuth2 + OIDC (OpenID Connect). Providers: Keycloak, Auth0, Okta, AWS Cognito, Azure AD.

Luồng trong microservices:

  1. User login ở Identity Provider (IdP) → nhận JWT (access + refresh + id token).
  2. Client gọi API Gateway với token.
  3. API Gateway verify token với IdP (qua public key/JWKS).
  4. Gateway forward request đến service, kèm user info.
  5. Mỗi service không cần login lại — chỉ verify JWT (self-contained).

Best practice:

  • Không tự làm auth — dùng IdP chuẩn.
  • JWT verify offline bằng public key (không gọi IdP mỗi request).
  • RBAC: role/permission trong JWT claims.
  • Refresh token rotation để tránh bị đánh cắp.
28. Các attack khác cần biết? (Clickjacking, SSRF, XXE, Path Traversal)
  • Clickjacking: lừa user click vào iframe ẩn. Prevent: header X-Frame-Options: DENY hoặc CSP frame-ancestors.
  • SSRF (Server-Side Request Forgery): lừa server gọi request đến internal service. Prevent: whitelist domain, chặn internal IP.
  • XXE (XML External Entity): inject external entity vào XML parser → đọc file server. Prevent: tắt external entity trong parser.
  • Path Traversal: ../../etc/passwd trong filename. Prevent: sanitize, dùng Paths.get(base).resolve(name).normalize() và check prefix.
  • Insecure Deserialization: deserialize object độc hại → RCE. Prevent: không dùng Java native serialization cho untrusted data.

5. System Design & High Concurrency

29. Rate Limiter là gì? Các thuật toán phổ biến?

Rate Limiter: giới hạn số request client gửi trong 1 khoảng thời gian.

Thuật toán:

  • Fixed Window: đếm theo cửa sổ cố định (0-60s). Nhược: burst ở biên (2x limit).
  • Sliding Window Log: lưu timestamp từng request. Chính xác nhưng tốn memory.
  • Sliding Window Counter: kết hợp counter 2 cửa sổ — cân bằng.
  • Token Bucket: bucket chứa N token, refill đều. Cho phép burst.
  • Leaky Bucket: request rò ra với tốc độ cố định. Làm phẳng traffic.

Implement với Redis (distributed):

-- Sliding window đơn giản
local count = redis.call('INCR', KEYS[1])
if count == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if count > tonumber(ARGV[2]) then return 0 end
return 1

Nếu limit không đủ → scale:

  • Tăng limit theo tier (user thường vs premium).
  • Sharding rate limiter theo user_id → mỗi Redis node quản 1 subset.
  • Dùng Redis Cluster hoặc Hazelcast.
  • Offload ở API Gateway (Kong, Nginx) thay vì app.

Trả về: HTTP 429 Too Many Requests + header Retry-After, X-RateLimit-Remaining.

30. Hệ thống bị latency cao 1 ngày — điều tra thế nào?

Bước 1 — Xác nhận & phạm vi:

  • Dashboard (Grafana): latency tăng từ khi nào? Ảnh hưởng endpoint nào? Tất cả user hay 1 số?
  • So sánh với baseline.

Bước 2 — Layer analysis (từ ngoài vào trong):

  • Network/DNS/LB: ping, traceroute, LB metrics.
  • Application: log, thread dump (jstack), APM (New Relic, Datadog).
  • DB: slow query log, connection pool metrics, lock waiting.
  • External services: latency của service thứ 3 (payment, email).
  • Infra: CPU, RAM, disk I/O, GC log.

Bước 3 — Xác định bottleneck:

  • p50 vs p99: nếu p99 cao, chỉ 1% request chậm (thường do GC hoặc lock).
  • Nếu toàn bộ chậm đều → infra hoặc DB.
  • Thread dump: xem thread nào đang BLOCKED/WAITING.
  • Heap dump: OOM hoặc memory leak.

Bước 4 — Fix & phòng ngừa:

  • Short-term: tăng pool size, restart, scale out, cache.
  • Long-term: index DB, optimize query, async, rate limit.
  • Setup alerting cho metric quan trọng trước khi user complain.
31. Nếu DB là nguyên nhân gây latency — tối ưu thế nào?

Query level:

  • Thêm index: cột trong WHERE, JOIN, ORDER BY.
  • Composite index: theo thứ tự selectivity cao → thấp.
  • EXPLAIN ANALYZE để xem execution plan.
  • Tránh: SELECT *, function trên indexed column (WHERE YEAR(created_at) = 2024 → không dùng index).
  • Covering index: index chứa cả cột select.

Schema level:

  • Denormalize khi cần (thêm cột computed).
  • Partition table lớn theo ngày/tháng.
  • Archive old data.

Application level:

  • Cache: Redis cho query hot.
  • Read replica: đọc từ replica, ghi vào master.
  • Connection pool tuning: HikariCP size hợp lý.
  • Batch insert/update: hibernate.jdbc.batch_size=50.
  • Fix N+1: JOIN FETCH, EntityGraph.

Kiến trúc level:

  • Sharding theo user_id/tenant.
  • NoSQL cho data phù hợp (time-series, log).
  • CQRS: tách read/write model.
32. Thiết kế hệ thống flash sale chịu tải cao?

Vấn đề: hàng nghìn request/s vào cùng 1 sản phẩm, cần tránh oversell, giữ hệ thống sống.

Kiến trúc:

  1. Rate limit ở API Gateway — chặn bot, giới hạn user.
  2. Queue hóa: đẩy request vào Kafka/RabbitMQ → xử lý tuần tự, giảm tải DB.
  3. Redis cache: lưu stock, decrement atomic (DECR, Lua script).
  4. Preload stock vào Redis trước flash sale.
  5. Optimistic lock hoặc pessimistic lock ở DB khi ghi đơn hàng.
  6. Idempotency key: 1 user chỉ tạo 1 đơn, retry không tạo 2.
  7. Holding page: trả về "đang xử lý" + polling kết quả (đỡ block request).

Tránh:

  • Không để mọi request chạm DB — dùng Redis làm stock counter.
  • Không dùng SELECT ... FOR UPDATE cho hàng trăm user đồng thời → deadlock.
  • Không dùng transaction dài giữ lock lâu.
-- Redis Lua script (atomic)
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
  redis.call('DECR', KEYS[1])
  return 1
end
return 0
33. Cascading failure là gì? Prevent thế nào?

Cascading failure: 1 service chết kéo theo service khác chết theo (domino).

Nguyên nhân: service A gọi B chậm → thread pool A cạn → A chết → C gọi A cũng chết.

Prevent:

  • Circuit Breaker (Resilience4j): fail fast khi downstream lỗi.
  • Timeout mọi external call (HTTP, DB).
  • Retry với backoff + jitter: tránh hammering.
  • Bulkhead: tách thread pool cho từng dependency → 1 cái lỗi không chiếm hết thread.
  • Fallback: trả cached data, empty list, hoặc default.
  • Rate limit để giảm tải khi có sự cố.
  • Health check + load balancer: loại bỏ instance unhealthy.
@CircuitBreaker(name = "payment", fallbackMethod = "fallback")
@Retry(name = "payment")
@TimeLimiter(name = "payment")
public CompletableFuture<Payment> pay(Order o) { ... }
34. Đo và cải thiện throughput thế nào?

Metrics chính:

  • Throughput: requests/second, transactions/second.
  • Latency: p50, p95, p99 (không dùng average — che giấu outlier).
  • Error rate: % request lỗi.
  • Saturation: CPU, memory, connection pool usage.

Cải thiện throughput:

  • Horizontal scale: thêm instance (stateless dễ).
  • Cache: Redis, Caffeine, HTTP cache.
  • Async & reactive: WebFlux, CompletableFuture cho I/O-bound.
  • Batch processing: gom nhiều request nhỏ thành batch.
  • DB tuning: index, connection pool, query optimization.
  • Compression: gzip cho response lớn.
  • Profiling: JProfiler, async-profiler để tìm hotspot.

Load test tool: JMeter, Gatling, k6, Locust.

Câu hỏi kinh điển: "Scale up vs scale out khác gì?" — up = tăng resource 1 máy; out = thêm máy. Scale out thường rẻ và resilient hơn.

6. Testing nâng cao

35. Line coverage vs Branch coverage?

Line coverage: % dòng code được chạy qua test.

Branch coverage: % nhánh (if/else, switch, ternary, short-circuit) được chạy qua cả true & false.

public String check(int x) {
  if (x > 0) return "positive";   // branch true
  return "non-positive";          // branch false
}
  • Test 1 lần với x = 5 → line coverage = 100% (cả 2 dòng chạy? Không — dòng return "non-positive" không chạy, nên ~66%).
  • Branch coverage = 50% (chỉ test true).
  • Test thêm x = -1 → branch = 100%.

Branch coverage chặt hơn. Industry thường target: line ≥ 80%, branch ≥ 70%.

Tool: JaCoCo, Cobertura, SonarQube.

36. Best practices khi viết unit test?
  • FIRST: Fast, Independent, Repeatable, Self-validating, Timely.
  • AAA hoặc Given-When-Then: Arrange - Act - Assert.
  • Tên test rõ ràng: findById_shouldThrow_whenNotFound().
  • 1 test 1 assert (hoặc 1 concept).
  • Không test implementation detail — test behavior.
  • Không dùng DB/network thật trong unit test → mock.
  • Test edge case: null, empty, max value, exception.
  • Không copy-paste test — dùng @ParameterizedTest.
  • Coverage không phải mục tiêu cuối — 100% coverage không có nghĩa 0 bug.

38. Reflection dùng để test private method thế nào? 
Method m = MyClass.class.getDeclaredMethod("privateMethod", int.class);
m.setAccessible(true);
Object result = m.invoke(instance, 42);

Khi nào dùng:

  • Test private method khi không có cách nào qua public API (dấu hiệu thiết kế kém).
  • Test utility class, helper.
  • Framework test (Mockito dùng reflection để inject mock).

Best practice:

  • Hạn chế dùng — private method nên được test qua public method.
  • Nếu private method phức tạp cần test riêng → nên tách ra class package-private hoặc utility.
  • Reflection phá vỡ encapsulation, dễ vỡ khi refactor.
39. Test pyramid vs Test trophy?

Test pyramid (Mike Cohn):

  • Unit test (đáy): nhiều nhất, nhanh, không I/O.
  • Integration test (giữa): vừa.
  • E2E/UI test (đỉnh): ít nhất, chậm, dễ vỡ.

Test trophy (Kent C. Dodds) — phù hợp frontend:

  • Static analysis (đáy).
  • Unit test (ít).
  • Integration test (nhiều nhất) — test qua API/UI thật.
  • E2E (ít).

Backend Java thường theo pyramid, với @WebMvcTest (integration nhẹ) làm trung tâm.

40. TDD là gì? Quy trình?

TDD (Test-Driven Development): viết test trước code.

Chu kỳ Red-Green-Refactor:

  1. Red: viết test fail (vì chưa có code).
  2. Green: viết code tối thiểu để test pass.
  3. Refactor: dọn code, vẫn đảm bảo test pass.

Lợi ích: thiết kế tốt hơn (testable), ít bug, regression an toàn.

Nhược điểm: chậm ban đầu, cần kỷ luật, không phù hợp với spike/POC.

Phỏng vấn hay hỏi: "Em viết test trước hay sau?" — câu trả lời trung thực: "Em thường viết test song song, với logic phức tạp thì viết test trước để clarify requirement."

7. Agile / Scrum

41. Agile là gì? Khác Waterfall?

Agile: triết lý phát triển phần mềm linh hoạt, chia nhỏ, lặp lại. 4 giá trị (Agile Manifesto):

  • Individual & interactions > processes & tools.
  • Working software > documentation.
  • Customer collaboration > contract negotiation.
  • Responding to change > following a plan.

Waterfall: tuần tự — requirement → design → code → test → deploy. Ổn định nhưng chậm thích ứng.

Agile: sprint ngắn (1–4 tuần), feedback liên tục, thích ứng thay đổi.

42. Scrum có mấy loại meeting? Mục đích?

5 sự kiện chính trong Scrum:

  1. Sprint Planning: đầu sprint — chọn backlog item cho sprint, estimate. Thời lượng ~2h cho sprint 2 tuần.
  2. Daily Standup: mỗi ngày 15 phút — 3 câu hỏi: hôm qua làm gì, hôm nay làm gì, có blocker gì.
  3. Sprint Review: cuối sprint — demo sản phẩm cho stakeholder, thu feedback.
  4. Sprint Retrospective: sau review — team nhìn lại: cái gì tốt, cái gì cần cải thiện, action item.
  5. Backlog Refinement (Grooming): giữa sprint — chuẩn bị backlog cho sprint sau.

Vai trò: Product Owner (WHAT), Scrum Master (process), Dev Team (HOW).

Artifact: Product Backlog, Sprint Backlog, Increment.

43. Story point vs man-hour? Velocity?
  • Story point: đơn vị tương đối đo độ phức tạp, không phải thời gian. Dùng Fibonacci (1, 2, 3, 5, 8, 13).
  • Man-hour: thời gian cụ thể. Dễ hiểu nhưng không chính xác.
  • Velocity: tổng story point hoàn thành mỗi sprint — dùng để dự đoán sprint sau.
  • Estimation techniques: Planning Poker, T-shirt size (S/M/L/XL).

Ý nghĩa: story point phản ánh effort + complexity + risk + uncertainty, không chỉ time.

8. Redis nâng cao

45. Redis là gì? Tại sao nhanh?

Redis: in-memory key-value store. Hỗ trợ String, List, Set, Sorted Set, Hash, Stream, HyperLogLog, Geo.

Nhanh vì:

  • In-memory: không đọc disk mỗi query.
  • Single-threaded cho command execution (không lock).
  • I/O multiplexing (epoll).
  • Data structure tối ưu.

Persistence: RDB (snapshot), AOF (append-only log). Có thể tắt nếu chỉ dùng cache.

Use case: cache, session store, rate limiter, leaderboard, message queue (Stream), distributed lock, pub/sub.

46. Redis distributed lock — SETNX? Redlock?

Cách đơn giản (single Redis):

SET lock_key unique_value NX PX 30000
-- NX: chỉ set nếu chưa tồn tại
-- PX 30000: TTL 30s (tránh deadlock nếu process crash)

Release lock phải atomic (dùng Lua) và chỉ release nếu value khớp (tránh xóa lock của người khác):

if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
end

Redlock (thuật toán của Redis author):

  • Dùng N (thường 5) Redis master độc lập.
  • Client lấy lock trên đa số (N/2 + 1) node trong thời gian ngắn.
  • Nếu thành công → lock acquired; ngược lại release.

Tranh cãi: Martin Kleppmann chỉ trích Redlock không an toàn trong 1 số tình huống (clock drift, GC pause). Nhiều dự án ưu tiên ZooKeeper, etcd, hoặc Redisson (Java lib) hơn.

Redisson cho Java:

RLock lock = redisson.getLock("myLock");
lock.lock(30, TimeUnit.SECONDS);
try { /* critical section */ }
finally { lock.unlock(); }
Phỏng vấn hay hỏi: "Nếu process giữ lock bị crash giữa chừng?" → TTL tự release. "Nếu xử lý lâu hơn TTL?" → Cần watchdog gia hạn lock (Redisson có sẵn).
47. Redis eviction policy?

Khi Redis đầy bộ nhớ, phải evict key. Các policy (maxmemory-policy):

  • noeviction: trả lỗi khi ghi.
  • allkeys-lru: xóa key ít dùng gần đây nhất (LRU). Phổ biến nhất cho cache.
  • allkeys-lfu: xóa key ít dùng nhất (LFU — tần suất).
  • allkeys-random: random.
  • volatile-lru / volatile-lfu / volatile-ttl: chỉ xóa trong số key có TTL.

Chọn:

  • Cache thuần → allkeys-lru.
  • Vừa cache vừa data quan trọng (không TTL) → volatile-lru.
  • Session store → volatile-lru + TTL.
48. Đo hiệu quả Redis cache thế nào?

Metrics chính (từ INFO stats):

  • Hit rate = hits / (hits + misses). Target > 80-90% cho cache tốt.
  • Evicted keys: nếu cao → cache thiếu bộ nhớ, tăng size hoặc giảm TTL.
  • Expired keys: bình thường, nhưng nếu quá nhiều → TTL quá ngắn.
  • Memory usage (INFO memory): used_memory, maxmemory.
  • Latency (redis-cli --latency): p50, p99.
  • Ops/sec: commands processed.
  • Connected clients: số connection đang mở.
  • Network I/O: bytes in/out.

Tools:

  • redis-cli info stats, redis-cli monitor (debug).
  • RedisInsight — UI chính thức.
  • Grafana + Prometheus với redis_exporter.
  • APM: Micrometer + Spring Boot Actuator (/actuator/metrics/cache.gets).
// Spring Boot cache metrics
cache.gets{name="users",result="hit"}
cache.gets{name="users",result="miss"}
cache.evictions{name="users"}
49. Redis Pub/Sub vs Stream?

Pub/Sub:

  • Fire-and-forget: subscriber offline → mất message.
  • Không lưu history.
  • Dùng cho: realtime notification, chat.

Stream (từ Redis 5.0):

  • Giống Kafka mini: message lưu, có ID, consumer group.
  • Hỗ trợ ack, replay.
  • Dùng cho: event queue nhẹ, không muốn thêm Kafka.

Chọn: cần delivery đảm bảo → Stream (hoặc Kafka). Realtime notification, mất message cũng được → Pub/Sub.

9. SQL Practice

50. Query: lấy khách hàng có tổng đơn > 5000?

Đề bài: bảng Customers(cust_id, name) và Orders(order_id, cust_id, amount). Lấy tất cả customer tồn tại trong Orders và tổng amount > 5000.

SELECT c.*
FROM Customers c
JOIN Orders o ON c.cust_id = o.cust_id
GROUP BY c.cust_id, c.name
HAVING SUM(o.amount) > 5000;

Cách khác với EXISTS:

SELECT c.*
FROM Customers c
WHERE EXISTS (
  SELECT 1 FROM Orders o
  WHERE o.cust_id = c.cust_id
  GROUP BY o.cust_id
  HAVING SUM(o.amount) > 5000
);

Chú ý:

  • WHERE filter trước GROUP BY; HAVING filter sau (trên aggregate).
  • Phải GROUP BY cả c.name nếu select ra (tùy DB — MySQL chấp nhận ONLY_FULL_GROUP_BY=off, PostgreSQL bắt buộc).
  • Nếu muốn khách không có đơn cũng hiện → LEFT JOIN + HAVING SUM(COALESCE(o.amount,0)) > 5000 (nhưng sẽ loại khách có sum=0).
51. Query: top 3 khách hàng chi nhiều nhất mỗi tháng? 
WITH monthly AS (
  SELECT c.cust_id, c.name,
         DATE_TRUNC('month', o.created_at) AS mth,
         SUM(o.amount) AS total,
         RANK() OVER (PARTITION BY DATE_TRUNC('month', o.created_at)
                      ORDER BY SUM(o.amount) DESC) AS rk
  FROM Customers c
  JOIN Orders o ON c.cust_id = o.cust_id
  GROUP BY c.cust_id, c.name, DATE_TRUNC('month', o.created_at)
)
SELECT * FROM monthly WHERE rk <= 3;

Điểm quan trọng:

  • Window function RANK() OVER (PARTITION BY ...) là chìa khóa cho "top N per group".
  • Dùng WITH (CTE) cho dễ đọc.
  • RANK vs DENSE_RANK vs ROW_NUMBER: rank nhảy số khi tie; dense không nhảy; row_number luôn unique.
52. Query: tìm customer không có order nào? 
-- LEFT JOIN + IS NULL
SELECT c.* FROM Customers c
LEFT JOIN Orders o ON c.cust_id = o.cust_id
WHERE o.cust_id IS NULL;

-- NOT EXISTS (thường nhanh hơn)
SELECT c.* FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.cust_id = c.cust_id);

-- NOT IN (cẩn thận với NULL)
SELECT c.* FROM Customers c
WHERE c.cust_id NOT IN (SELECT cust_id FROM Orders WHERE cust_id IS NOT NULL);

Lưu ý: NOT IN với subquery chứa NULL → trả về empty. Luôn filter NULL hoặc dùng NOT EXISTS.

53. Query: tìm duplicate rows? 
-- Tìm email trùng
SELECT email, COUNT(*) as cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

-- Xóa duplicate, giữ id nhỏ nhất
DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email
);

PostgreSQL / MySQL 8+ (window function):

WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
  FROM users
)
DELETE FROM users WHERE id IN (SELECT id FROM ranked WHERE rn > 1);
54. Query: tìm employee có lương cao thứ 2? 
-- Subquery
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- Window function (rõ ràng hơn)
SELECT * FROM (
  SELECT *, DENSE_RANK() OVER (ORDER BY salary DESC) AS rk
  FROM employees
) t WHERE rk = 2;

Chú ý: nếu có nhiều người cùng lương cao thứ 2 → dùng DENSE_RANK. Nếu muốn 1 người bất kỳ → ROW_NUMBER.

55. Index — khi nào dùng? Khi nào không?

Dùng index khi:

  • Cột thường xuyên trong WHERE, JOIN, ORDER BY.
  • Cột có high cardinality (nhiều giá trị unique: email, id).
  • Foreign key.
  • Composite index cho query có nhiều điều kiện (thứ tự quan trọng).

Không nên index:

  • Cột low cardinality (giới tính, status ít giá trị).
  • Bảng nhỏ (vài nghìn row).
  • Cột ít query.
  • Bảng write-heavy (index làm chậm insert/update).

Loại index: B-tree (default), Hash, GIN (full-text, JSONB), GiST (geometry), BRIN (large sequential).

Câu hỏi mở rộng: "Tại sao index làm chậm insert?" → Mỗi lần insert phải update cả index → tăng I/O và lock.

10. Microservices nâng cao

56. Microservices giao tiếp với nhau thế nào?

2 kiểu chính:

  • Synchronous: REST (HTTP/JSON), gRPC (HTTP/2 + Protobuf). Yêu cầu response ngay.
  • Asynchronous: message queue (Kafka, RabbitMQ), event-driven. Không chờ response.

REST vs gRPC:

  • Public API, browser → REST.
  • Internal service-to-service, hiệu năng cao → gRPC.

57. Tracing giữa các service — implement thế nào?

Distributed Tracing: theo dõi 1 request xuyên nhiều service.

Khái niệm:

  • Trace ID: định danh request xuyên suốt.
  • Span ID: định danh từng bước trong 1 service.
  • Parent Span: span cha — tạo thành cây.

Chuẩn: OpenTelemetry (OTel) — thay thế OpenTracing + OpenCensus.

Implement trong Spring Boot:

<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>

Cách hoạt động:

  • Service A sinh trace ID khi nhận request.
  • Khi gọi service B (REST/gRPC/Kafka), trace ID được truyền qua header (traceparent) hoặc message header.
  • B tiếp tục span với cùng trace ID.
  • Mọi span được gửi đến collector (Jaeger, Zipkin, Tempo, Datadog).

Tool: Jaeger, Zipkin, Grafana Tempo, AWS X-Ray, Datadog APM.

MDC logging: đưa trace ID vào log để correlate log giữa service.

logging.pattern.level=%5p [${spring.application.name},%X{traceId:-},%X{spanId:-}]
58. External service call — quản lý thread/connection thế nào?

Vấn đề: mỗi request đến external service cần thread + connection. Nếu không quản lý → thread pool cạn, memory leak, cascade failure.

Giải pháp:

  • Connection pool + Timeout cho HTTP client: 
    @Bean
public RestTemplate restTemplate() {
  HttpComponentsClientHttpRequestFactory f = new HttpComponentsClientHttpRequestFactory();
  f.setConnectTimeout(3000);
  f.setReadTimeout(5000);
  return new RestTemplate(f);
}
  • Circuit Breaker (Resilience4j): fail fast khi external chết.
  • Bulkhead: giới hạn số thread đồng thời gọi 1 external → không chiếm hết thread pool.
  • Retry với exponential backoff + jitter: 
    @Retry(name = "payment", fallbackMethod = "fallback")
@Backoff(delay = 1000, multiplier = 2)
public Payment pay() { ... }
  • Async: dùng WebClient (reactive) hoặc @Async — không block thread.
  • Cache response nếu có thể.
  • Fallback: trả giá trị mặc định, cached, hoặc queue lại.
@CircuitBreaker(name = "payment", fallbackMethod = "fallback")
@Bulkhead(name = "payment", type = Type.THREADPOOL)
@Retry(name = "payment")
@TimeLimiter(name = "payment")
public CompletableFuture<Payment> pay(Order o) { ... }
59. Kafka transactions là gì?

Mục đích: đảm bảo exactly-once semantics khi produce message — hoặc tất cả thành công, hoặc không message nào được ghi.

Cách hoạt động:

  1. Producer có transactional.id cố định.
  2. initTransactions() → đăng ký với broker.
  3. beginTransaction() → bắt đầu.
  4. Produce nhiều message (có thể nhiều partition/topic).
  5. commitTransaction() hoặc abortTransaction().
producer.initTransactions();
try {
  producer.beginTransaction();
  producer.send(record1);
  producer.send(record2);
  producer.commitTransaction();
} catch (Exception e) {
  producer.abortTransaction();
}

Consumer side: đọc với isolation.level=read_committed để không đọc message từ transaction chưa commit.

Use case:

  • Read-Process-Write: đọc từ topic A, xử lý, ghi vào topic B — atomic.
  • Đảm bảo khi crash giữa chừng, không ghi nửa vời.

Spring Kafka:

@Transactional
@KafkaListener(topics = "input")
public void listen(String msg) {
  // xử lý + gửi sang topic khác, tất cả trong 1 Kafka transaction
}

Hạn chế: chỉ trong Kafka, không span tới DB. Muốn atomic với DB → dùng Outbox Pattern hoặc Saga.

60. Design message cho Kafka/RabbitMQ — best practices?

Nguyên tắc chung:

  • Schema evolution: thêm field optional > xóa field. Dùng Avro/Protobuf + Schema Registry.
  • Versioning: có field eventVersion hoặc topic user.created.v2.
  • Idempotency key: eventId để consumer dedupe.
  • Timestamp: occurredAt (khi event xảy ra) + publishedAt (khi publish).
  • Correlation ID: để trace.
  • Payload nhỏ: gửi ID + tham chiếu, không gửi blob lớn.

Nên làm:

  • Message là event (sự kiện đã xảy ra), không phải command: OrderCreated thay vì CreateOrder.
  • Immutable.
  • Có metadata (headers) tách khỏi payload.
  • Consumer phải idempotent — vì message có thể đến 2 lần (at-least-once).

Tránh:

  • Payload chứa toàn bộ entity lớn (kèm nested object, image base64).
  • Phụ thuộc vào thứ tự field.
  • Dùng Java native serialization (Serializable) → không cross-language, dễ vỡ khi refactor.
  • Breaking change: đổi type, xóa field bắt buộc.
  • Business logic trong message (consumer phải hiểu).
{
  "eventId": "uuid",
  "eventType": "OrderCreated",
  "eventVersion": 1,
  "occurredAt": "2024-01-01T10:00:00Z",
  "correlationId": "trace-abc",
  "payload": {
    "orderId": 123,
    "customerId": 456,
    "total": 99.99
  }
}
61. Serverless là gì? Ưu nhược điểm?

Serverless: không quản lý server, cloud tự scale, trả tiền theo request/thời gian chạy. Gồm FaaS (Function-as-a-Service) + BaaS (Backend-as-a-Service).

Ví dụ: AWS Lambda, Google Cloud Functions, Azure Functions.

Ưu điểm:

  • Không quản lý infra, tự scale 0 → vô hạn.
  • Trả tiền theo dùng (pay-per-invocation).
  • Deploy nhanh, nhỏ gọn.

Nhược điểm:

  • Cold start: function chưa chạy lần nào → khởi động chậm (Java đặc biệt — có thể 1-3s).
  • Giới hạn timeout (Lambda 15 phút).
  • Khó debug, khó test local.
  • Vendor lock-in.
  • Không phù hợp cho long-running, stateful, high-throughput liên tục.

Spring Cloud Function cho phép viết function theo kiểu Spring chạy trên Lambda.

Khi nào dùng: event-driven, traffic thất thường (cron, webhook), glue code. Không dùng: API throughput cao liên tục, WebSocket, ML training.

62. Autowiring modes trong Spring?

Spring hỗ trợ 4 mode autowiring (có thể cấu hình qua XML; với annotation thì dùng @Autowired):

  • no (mặc định): không autowire — phải khai báo thủ công.
  • byName: inject theo tên bean — tương ứng @Autowired @Qualifier("beanName").
  • byType: inject theo type — mặc định của @Autowired.
  • constructor: inject qua constructor — tương đương constructor injection (khuyến nghị).

Với @Autowired, resolution order:

  1. Match theo type.
  2. Nếu nhiều bean → fallback theo @Primary, sau đó @Qualifier, sau đó theo bean name (khớp với tên field/parameter).
  3. Nếu vẫn ambiguous → NoUniqueBeanDefinitionException.

Limitations:

  • Primitive types: không autowire được int, String... vì không phải bean — phải dùng @Value.
  • Ambiguity: nhiều bean cùng type → cần @Qualifier/@Primary.
  • Khó debug: lỗi inject chỉ vỡ khi runtime, không compile-time.
  • Không explicit dependency: field injection che giấu dependency.
@Service
public class MyService {
  @Value("${app.timeout:5000}") private int timeout;  // primitive
  @Autowired @Qualifier("vnPay") private PaymentGateway gateway;  // byName
}
63. Điều gì xảy ra khi thêm Spring Security starter?

Khi thêm spring-boot-starter-security:

  1. Auto-config kích hoạt SecurityAutoConfiguration + UserDetailsServiceAutoConfiguration.
  2. Toàn bộ endpoint bị bảo vệ mặc định — phải login mới truy cập.
  3. Form login + HTTP Basic tự bật.
  4. User mặc định được tạo: username user, password random in ra log khi khởi động: 
    Using generated security password: 3e4a5c8f-...
  5. Filter chain được setup: UsernamePasswordAuthenticationFilter, BasicAuthenticationFilter, CsrfFilter...
  6. CSRF bật mặc định cho form-based.
  7. Session-based auth mặc định.
  8. Session fixation protection, security headers (X-Content-Type-Options, X-Frame-Options).

Cần config lại:

  • Định nghĩa SecurityFilterChain bean để custom rules.
  • Cấu hình PasswordEncoder (BCrypt).
  • Định nghĩa UserDetailsService để load user từ DB.
  • Tắt CSRF nếu làm REST API + JWT.
  • Chuyển sang stateless session nếu dùng JWT.
Đây là câu hỏi rất phổ biến — nhấn mạnh: "Khi thêm starter, mọi thứ tự động bảo vệ, phải override lại".
64. Logging khác nhau giữa local/QA/Prod — cấu hình thế nào?

Cách 1: Profile + application-{env}.yml

# application-dev.yml
logging:
  level:
    root: DEBUG
    com.example: DEBUG
    org.hibernate.SQL: DEBUG

# application-qa.yml
logging:
  level:
    root: INFO
    com.example: INFO
  file:
    name: /var/log/app/app.log

# application-prod.yml
logging:
  level:
    root: WARN
    com.example: INFO
  file:
    name: /var/log/app/app.log
    max-size: 100MB
    max-history: 30

Cách 2: logback-spring.xml với <springProfile>

<springProfile name="dev">
  <root level="DEBUG">
    <appender-ref ref="CONSOLE"/>
  </root>
</springProfile>

<springProfile name="prod">
  <root level="INFO">
    <appender-ref ref="ROLLING"/>
  </root>
</springProfile>

Best practice:

  • Local: console log, level DEBUG, có SQL, có trace ID.
  • QA/Test: file log, INFO, JSON format để parse dễ.
  • Prod: JSON log (ELK/CloudWatch parse), INFO/WARN, masking sensitive data (password, token), rolling + retention.
  • Dùng MDC để thêm trace ID, user ID vào mọi log line.
  • Không log System.out.println — dùng SLF4J.
  • Không log exception mà quên stacktrace.

Runtime change level (không cần restart):

POST /actuator/loggers/com.example
{ "configuredLevel": "DEBUG" }
