1. Servlet & Servlet Container

Servlet là gì?

Servlet là 1 class Java implement interface jakarta.servlet.Servlet — nhận HTTP request và trả HTTP response. Ra đời 1997 như chuẩn Java EE để xử lý web.

Servlet interface — rút gọn
public interface Servlet {
    void init(ServletConfig config) throws ServletException;
    void service(ServletRequest req, ServletResponse res) throws ServletException, IOException;
    void destroy();
    ServletConfig getServletConfig();
    String getServletInfo();
}

Servlet Container là gì?

Servlet Container (Tomcat, Jetty, Undertow) — chương trình Java quản lý vòng đời servlet, parse HTTP, quản lý thread pool.

Nhiệm vụ:

  • Parse HTTP request thành HttpServletRequest object.
  • Map request URL → servlet tương ứng.
  • Quản lý lifecycle servlet (init → service → destroy).
  • Quản lý thread pool — 1 request = 1 thread.
  • Convert response → HTTP bytes gửi client.

Servlet lifecycle

1. Container khởi động │ 2. new ServletClass() ← tạo instance │ 3. servlet.init(config) ← gọi 1 lần, nhận config │ 4. servlet.service(req, res) ← gọi MỖI request │ ├─ HttpServlet.service() phân loại theo method │ ├─ Gọi doGet() nếu GET │ ├─ Gọi doPost() nếu POST │ └─ ... │ 5. Container shutdown │ 6. servlet.destroy() ← gọi 1 lần, cleanup
Đào sâu — tại sao Servlet là singleton? Servlet instance được tạo 1 lần, dùng chung cho mọi request. Vì vậy servlet phải thread-safe — không được có mutable field. Đây cũng là lý do Spring bean mặc định phải stateless.

Ví dụ — Servlet thuần (không Spring)

@WebServlet("/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse res)
            throws IOException {
        String name = req.getParameter("name");
        res.setContentType("application/json");
        res.getWriter().write("{\"msg\":\"Hello " + name + "\"}");
    }
}

Vấn đề khi không có Spring:

  • Mỗi URL = 1 servlet → 100 endpoint = 100 class.
  • Không có DI — mọi dependency phải tự new.
  • Không có AOP, transaction, validation.
  • Không có view resolver, message converter.
  • Code lặp lại khủng khiếp.
Spring MVC ra đời để giải quyết: thay vì 100 servlet, chỉ cần 1 DispatcherServlet — Front Controller điều phối mọi request.
Câu hỏi: "Servlet lifecycle có mấy bước?"
Trả lời: 3 bước — init() gọi 1 lần khi tạo, service() gọi mỗi request (phân loại sang doGet/doPost...), destroy() gọi 1 lần khi shutdown. Servlet là singleton.

doDispatch() — Trái tim của DispatcherServlet

Đây là method điều phối toàn bộ — mình sẽ trích source rút gọn:

Spring source — DispatcherServlet.doDispatch() (rút gọn)
protected void doDispatch(HttpServletRequest request,
                          HttpServletResponse response) throws Exception {
    HttpServletRequest processedRequest = request;
    HandlerExecutionChain mappedHandler = null;
    ModelAndView mv = null;

    try {
        // 1. Check multipart (file upload)
        processedRequest = checkMultipart(request);

        // 2. TÌM HANDLER
        mappedHandler = getHandler(processedRequest);
        if (mappedHandler == null) {
            noHandlerFound(processedRequest, response);
            return;   // 404
        }

        // 3. TÌM ADAPTER cho handler
        HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());

        // 4. GỌI preHandle của interceptor
        if (!mappedHandler.applyPreHandle(processedRequest, response)) {
            return;   // interceptor chặn
        }

        // 5. GỌI CONTROLLER qua adapter
        mv = ha.handle(processedRequest, response, mappedHandler.getHandler());

        // 6. GỌI postHandle
        mappedHandler.applyPostHandle(processedRequest, response, mv);

    } catch (Exception ex) {
        // 7. XỬ LÝ EXCEPTION
        dispatchException = ex;
    }

    // 8. RENDER view / serialize response
    processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);

    // 9. GỌI afterCompletion
    if (mappedHandler != null) {
        mappedHandler.triggerAfterCompletion(request, response, null);
    }
}
Đào sâu: Toàn bộ request flow của Spring MVC nằm trong ~40 dòng của doDispatch(). Đây là hàm bạn nên đọc 1 lần trong đời — hiểu nó = hiểu cả Spring MVC.

Match rules khi có request

Khi request GET /api/users/123 đến, HandlerMapping phải match:

  1. URL pattern: /api/users/{id} match /api/users/123 → id = 123.
  2. HTTP method: GET phải khớp @GetMapping.
  3. Consumes: Content-Type của request phải match (nếu có khai báo).
  4. Produces: Accept header của client phải match.
  5. Headers: nếu có khai báo headers = "X-Api-Version=1".
  6. Params: nếu có khai báo params = "action=create".

Priority khi nhiều handler match

Nếu 2 mapping cùng match, Spring dùng Comparator xếp hạng:

  • Path cụ thể hơn thắng: /users/admin > /users/{id}.
  • Có consumes/produces cụ thể thắng.
  • Nhiều điều kiện hơn thắng.
Đào sâu — PathPattern (Spring 5.3+): Spring cũ dùng AntPathMatcher (String-based, chậm). Spring mới dùng PathPatternParser — parse pattern thành object 1 lần, match nhanh hơn, an toàn hơn với path traversal. Bật qua spring.mvc.pathmatch.matching-strategy=path_pattern_parser.

Khi không tìm thấy handler

getHandler() trả về null → DispatcherServlet gọi noHandlerFound():

  • Nếu throwExceptionIfNoHandlerFound=true → ném NoHandlerFoundException → 404 qua exception resolver.
  • Ngược lại → gửi 404 trực tiếp.
Câu hỏi: "HandlerMapping hoạt động thế nào?"
Trả lời: Lúc startup, RequestMappingHandlerMapping scan mọi bean, tìm class có @Controller, đọc annotation method, build bảng routing URL → HandlerMethod. Khi có request, tra bảng, match URL + method + headers → trả về HandlerExecutionChain (handler + interceptors).

4. HandlerAdapter — Gọi controller

Tại sao cần HandlerAdapter?

Câu hỏi tự nhiên: DispatcherServlet có handler rồi — sao không gọi trực tiếp mà cần Adapter?

Vì có nhiều loại handler khác nhau:

  • @RequestMapping method — cần resolve tham số, xử lý return value.
  • HttpRequestHandler — interface cũ, gọi thẳng.
  • @Controller với @ResponseBody.
  • Servlet, Filter — cần wrap.
  • Router Function (Spring 5+).

Mỗi loại handler có cách gọi khác nhau. DispatcherServlet không muốn biết hết → dùng Adapter pattern.

Ổ cắm điện VN là 2 chân dẹt. Ổ châu Âu là 2 chân tròn. Bạn có nhiều thiết bị khác nhau → dùng adapter để cắm. DispatcherServlet là ổ cắm — nó cần adapter cho từng loại handler.

Các implementation của HandlerAdapter

Cách DispatcherServlet chọn adapter

DispatcherServlet
protected HandlerAdapter getHandlerAdapter(Object handler) {
    for (HandlerAdapter adapter : this.handlerAdapters) {
        if (adapter.supports(handler)) {   // ← hỏi từng adapter
            return adapter;
        }
    }
    throw new ServletException("No adapter for handler: " + handler);
}

RequestMappingHandlerAdapter hoạt động thế nào?

Đây là adapter chính — xử lý @RequestMapping method:

RequestMappingHandlerAdapter.handle() │ 1. Cast handler → HandlerMethod │ 2. Tạo ServletInvocableHandlerMethod │ (wrap method + bean) │ 3. Chuẩn bị ArgumentResolvers │ (danh sách resolver để bind tham số) │ 4. Chuẩn bị ReturnValueHandlers │ (danh sách handler để xử lý return) │ 5. Bind + invoke: │ ├─ resolveArguments() → bind @RequestParam, @PathVariable... │ ├─ method.invoke() → gọi controller method │ └─ handleReturnValue() → serialize response │ 6. Return ModelAndView (null nếu @ResponseBody)

HandlerMethod — object bao quanh method

public class HandlerMethod {
    private final Object bean;          // controller instance
    private final Method method;        // reflection Method
    private final MethodParameter[] parameters;
    private final Class<?> beanType;
    // ...
}

HandlerMethod cung cấp:

  • Truy cập annotation trên method: getMethodAnnotation().
  • Truy cập parameter metadata: getMethodParameters().
  • Invoke với argument đã resolve sẵn.
Đào sâu — Adapter pattern: Đây là ví dụ kinh điển của Adapter. Bạn có interface cũ (HandlerAdapter.supports()) và nhiều loại handler khác nhau (@RequestMapping, HttpRequestHandler...). Adapter giúp chúng work cùng nhau mà không sửa code gốc.
Câu hỏi: "Tại sao cần HandlerAdapter, không gọi controller trực tiếp?"
Trả lời: Vì có nhiều loại handler khác nhau (annotation-based, HttpRequestHandler, Router Function). Mỗi loại cần cách gọi khác nhau. HandlerAdapter là Adapter pattern — DispatcherServlet không cần biết chi tiết, chỉ cần tìm adapter phù hợp. Nhờ đó có thể thêm loại handler mới mà không sửa DispatcherServlet.

5. HandlerInterceptor — Chặn request

Interface HandlerInterceptor

Spring source
public interface HandlerInterceptor {

    // Chạy TRƯỚC handler
    // return true  → đi tiếp
    // return false → dừng, không vào handler
    default boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response,
                              Object handler) throws Exception {
        return true;
    }

    // Chạy SAU handler, TRƯỚC render view
    // Chỉ chạy nếu preHandle return true và handler không exception
    default void postHandle(HttpServletRequest request,
                            HttpServletResponse response,
                            Object handler,
                            @Nullable ModelAndView modelAndView) throws Exception { }

    // Chạy SAU khi request hoàn tất (kể cả exception)
    // Chỉ chạy nếu preHandle của interceptor này return true
    default void afterCompletion(HttpServletRequest request,
                                 HttpServletResponse response,
                                 Object handler,
                                 @Nullable Exception ex) throws Exception { }
}

Thứ tự chạy khi có nhiều interceptor

registry.addInterceptor(intA);   // order = 0
registry.addInterceptor(intB);   // order = 1
registry.addInterceptor(intC);   // order = 2
Request → │ ├─ intA.preHandle() → true ├─ intB.preHandle() → true ├─ intC.preHandle() → true │ ▼ Controller xử lý │ ▼ ├─ intC.postHandle() ├─ intB.postHandle() ├─ intA.postHandle() │ ▼ Render view │ ▼ ├─ intC.afterCompletion() ├─ intB.afterCompletion() ├─ intA.afterCompletion() │ ▼ Response → Client

Quy tắc: preHandle chạy xuôi thứ tự đăng ký. postHandle và afterCompletion chạy ngược.

Ví dụ thực tế — Request ID Interceptor

@Component
@Slf4j
public class RequestIdInterceptor implements HandlerInterceptor {

    private static final String HEADER = "X-Request-Id";
    private static final String MDC_KEY = "requestId";

    @Override
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res,
                             Object handler) {
        String requestId = req.getHeader(HEADER);
        if (requestId == null || requestId.isBlank()) {
            requestId = UUID.randomUUID().toString();
        }
        MDC.put(MDC_KEY, requestId);
        res.setHeader(HEADER, requestId);
        log.info(">>> {} {}", req.getMethod(), req.getRequestURI());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req,
                                HttpServletResponse res,
                                Object handler,
                                Exception ex) {
        log.info("<<< {} {} — done", req.getMethod(), req.getRequestURI());
        MDC.clear();   // ← QUAN TRỌNG: cleanup để tránh leak
    }
}

Đăng ký Interceptor

@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {

    private final RequestIdInterceptor requestIdInterceptor;
    private final AuthInterceptor authInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // Áp dụng cho mọi URL
        registry.addInterceptor(requestIdInterceptor)
                .addPathPatterns("/**");

        // Chỉ áp dụng cho /api/**
        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns(
                    "/api/auth/login",
                    "/api/auth/register",
                    "/api/public/**"
                )
                .order(1);
    }
}

Auth Interceptor — Ví dụ

@Component
@RequiredArgsConstructor
public class AuthInterceptor implements HandlerInterceptor {

    private final JwtService jwtService;

    @Override
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res,
                             Object handler) throws IOException {

        // Bỏ qua CORS preflight
        if ("OPTIONS".equalsIgnoreCase(req.getMethod())) {
            return true;
        }

        // Không phải HandlerMethod → skip
        if (!(handler instanceof HandlerMethod)) {
            return true;
        }

        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            res.setStatus(401);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"Missing token\"}");
            return false;   // ← DỪNG
        }

        String token = header.substring(7);
        if (!jwtService.isValid(token)) {
            res.setStatus(401);
            res.getWriter().write("{\"error\":\"Invalid token\"}");
            return false;
        }

        // Lưu thông tin để controller dùng
        req.setAttribute("userId", jwtService.extractUserId(token));
        return true;
    }
}

Lưu ý quan trọng

postHandle KHÔNG chạy nếu controller ném exception. Khi exception xảy ra, flow nhảy thẳng đến afterCompletion qua exception resolver. Đây là lý do cleanup thường đặt trong afterCompletion, không phải postHandle.
MDC.clear() rất quan trọng. Vì Tomcat dùng thread pool — thread được tái sử dụng. Nếu bạn MDC.put() mà không MDC.clear(), log của request sau sẽ bị "lẫn" requestId cũ.
Đào sâu — Interceptor có phải bean không? Có. Interceptor phải là bean (@Component) để có thể inject dependency (như JwtService). Nhưng phải đăng ký qua WebMvcConfigurer — không tự động apply như @Component thông thường.
Câu hỏi: "Interceptor có mấy method? Khác nhau chỗ nào?"
Trả lời: 3 method — preHandle chạy trước controller, return false để chặn. postHandle chạy sau controller, trước render view — KHÔNG chạy nếu có exception. afterCompletion chạy sau cùng, kể cả có exception — dùng để cleanup.

Custom Argument Resolver — Khi nào cần?

Ví dụ — tự tạo @CurrentUser annotation để inject user đang login:

@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface CurrentUser { }

@Component
public class CurrentUserResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(CurrentUser.class);
    }

    @Override
    public Object resolveArgument(MethodParameter parameter,
                                  ModelAndViewContainer mav,
                                  NativeWebRequest req,
                                  WebDataBinderFactory factory) {
        // Đọc userId từ SecurityContext
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        return userService.findByUsername(auth.getName());
    }
}

// Đăng ký
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new CurrentUserResolver());
    }
}

// Dùng
@GetMapping("/me")
public UserDto me(@CurrentUser User user) {
    return UserMapper.toDto(user);
}
Đào sâu — tại sao resolver phải sort theo Order? Vì có thể nhiều resolver cùng supportsParameter = true. Ví dụ @RequestParam String name — cả RequestParamMethodArgumentResolver và ServletModelAttributeMethodProcessor đều có thể handle. Order quyết định resolver nào thắng.
Câu hỏi: "Làm sao Spring bind @RequestBody thành object?"
Trả lời: RequestResponseBodyMethodProcessor (một ArgumentResolver) hỗ trợ parameter có @RequestBody. Khi resolve, nó đọc Content-Type, chọn HttpMessageConverter (Jackson cho JSON), gọi read() để parse input stream thành object. Nếu có @Valid, gọi Validator sau đó.

7. HttpMessageConverter — Serialize/Deserialize

Vai trò

HttpMessageConverter chuyển đổi giữa:

  • HTTP body (bytes) ↔ Java object.
  • Dùng cho cả @RequestBody (đọc) và @ResponseBody (ghi).
Spring source
public interface HttpMessageConverter<T> {

    // Converter có đọc được mediaType → class này không?
    boolean canRead(Class<?> clazz, @Nullable MediaType mediaType);

    // Converter có ghi được class này → mediaType không?
    boolean canWrite(Class<?> clazz, @Nullable MediaType mediaType);

    // Đọc từ input stream → object
    T read(Class<? extends T> clazz, HttpInputMessage inputMessage) throws IOException;

    // Ghi object → output stream
    void write(T t, @Nullable MediaType contentType, HttpOutputMessage outputMessage) throws IOException;
}

public class YamlHttpMessageConverter extends AbstractHttpMessageConverter<Object> {

    public YamlHttpMessageConverter() {
        super(new MediaType("application", "yaml"));
        this.yamlMapper = new ObjectMapper(new YAMLFactory());

    protected boolean supports(Class<?> clazz) {

    protected Object readInternal(Class<?> clazz, HttpInputMessage inputMessage)

        return yamlMapper.readValue(inputMessage.getBody(), clazz);
    }

    @Override
    protected void writeInternal(Object o, HttpOutputMessage outputMessage)
            throws IOException {
        yamlMapper.writeValue(outputMessage.getBody(), o);
    }
}

@RestControllerAdvice — Chi tiết

@RestControllerAdvice   // ← @ControllerAdvice + @ResponseBody
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
        log.warn("Not found: {}", ex.getMessage());
        return new ErrorResponse("NOT_FOUND", ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                FieldError::getDefaultMessage,
                (a, b) -> a
            ));
        return new ErrorResponse("VALIDATION_ERROR", "Dữ liệu không hợp lệ", errors);
    }

    @ExceptionHandler(DataIntegrityViolationException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ErrorResponse handleConflict(DataIntegrityViolationException ex) {
        log.error("DB conflict", ex);
        return new ErrorResponse("CONFLICT", "Duplicate or constraint violation");
    }

    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ErrorResponse handleAll(Exception ex) {
        log.error("Unexpected error", ex);
        return new ErrorResponse("INTERNAL_ERROR", "Unexpected error occurred");
    }
}

Cơ chế match exception

Exception được ném ra: ResourceNotFoundException ExceptionHandlerExceptionResolver: │ ├─ Tra bảng @ExceptionHandler │ ├─ Tìm handler match chính xác ResourceNotFoundException │ → GlobalExceptionHandler.handleNotFound() │ ├─ Nếu không có → tìm theo class cha │ → Exception.class handler │ └─ Nguyên tắc: CỤ THỂ thắng

Thứ tự ưu tiên — Ví dụ

@ExceptionHandler(RuntimeException.class)         // #1
@ExceptionHandler(IllegalStateException.class)    // #2
@ExceptionHandler(ResourceNotFoundException.class)// #3 (con của IllegalStateException)

Nếu ném ResourceNotFoundException:

  • Spring chọn #3 — cụ thể nhất.
  • Nếu #3 không có → chọn #2.
  • Nếu #2 không có → chọn #1.

Exception trong Filter — Tại sao @ExceptionHandler không bắt được?

Request │ ▼ ┌────────────────────────────────┐ │ Filter Chain │ ← Exception ở đây KHÔNG bắt được │ (Security, CORS...) │ bởi @ExceptionHandler └────────────────────────────────┘ │ ▼ DispatcherServlet │ ▼ @ExceptionHandler ← Chỉ bắt được exception từ controller trở xuống

Lý do: Filter chạy trước DispatcherServlet. Exception từ Filter không đi qua ExceptionHandlerExceptionResolver — nó đi trực tiếp ra Servlet Container.

Cách xử lý exception trong Filter:

@Component
public class JwtFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws IOException {
        try {
            // validate token
            chain.doFilter(req, res);
        } catch (JwtException ex) {
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"" + ex.getMessage() + "\"}");
            // Không throw ra ngoài
        }
    }
}
Lưu ý: Nếu Filter throw exception không được catch, Tomcat sẽ dùng ErrorPage — không đi qua @RestControllerAdvice. Phải tự xử lý trong Filter.
Câu hỏi: "@RestControllerAdvice có bắt được exception từ Filter không?"
Trả lời: Không. Vì Filter chạy trước DispatcherServlet, exception từ Filter không đi qua ExceptionHandlerExceptionResolver. Phải tự try-catch trong Filter và ghi response thủ công.

PART 1: FILTER — Tầng Servlet Container

Định nghĩa

Filter là 1 interface thuộc Servlet API (jakarta.servlet.Filter) — không phải Spring. Nó chặn request/response ở tầng Servlet Container (Tomcat), trước khi vào DispatcherServlet.

Servlet API — Filter interface

    // Chuỗi filter: mỗi filter chạy doFilter
    // Phải gọi chain.doFilter() để đi tiếp

Cách cài đặt Filter

Cách 1: implement Filter + @Component

@Component
@Order(1)   // ← thứ tự chạy
@Slf4j
public class RequestLoggingFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request,
                         ServletResponse response,
                         FilterChain chain) throws IOException, ServletException {

        HttpServletRequest req = (HttpServletRequest) request;
        long start = System.currentTimeMillis();

        log.info("BEGIN {} {}", req.getMethod(), req.getRequestURI());

        try {
            chain.doFilter(request, response);   // ← QUAN TRỌNG: đi tiếp
        } finally {
            long duration = System.currentTimeMillis() - start;
            log.info("END {} {} — {}ms",
                     req.getMethod(), req.getRequestURI(), duration);
        }
    }
}

Phân tích — Có Filter vs Không có Filter

❌ Không có Filter
  • Không thể set encoding UTF-8 trước khi Spring đọc body → tiếng Việt lỗi.
  • Không thể xử lý CORS ở tầng thấp → browser chặn preflight.
  • Không thể chặn request quá sớm — ví dụ rate limit theo IP trước khi vào DispatcherServlet.
  • Không thể wrap request để đọc body nhiều lần (logging).
  • Không thể xác thực trước khi Spring MVC parse request.
✅ Có Filter
  • Set UTF-8 cho mọi request/response.
  • Xử lý CORS toàn cục.
  • Rate limit theo IP trước khi tốn tài nguyên Spring.
  • Wrap request bằng ContentCachingRequestWrapper.
  • Security filter chain (Spring Security).
  • Compress response (gzip).

Hạn chế của Filter

  • Không biết controller nào sắp chạy — chỉ có request thô.
  • Không có Spring context đầy đủ — phải inject qua constructor.
  • Không truy cập được ModelAndView.
  • Không truy cập SecurityContext mặc định (phải set sau filter khác).

Cách cài đặt Interceptor

@Component
@RequiredArgsConstructor
@Slf4j
public class AuthInterceptor implements HandlerInterceptor {

    private final JwtService jwtService;

    @Override
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res,
                             Object handler) throws IOException {

        if ("OPTIONS".equalsIgnoreCase(req.getMethod())) return true;
        if (!(handler instanceof HandlerMethod)) return true;

        String token = extractToken(req);
        if (token == null || !jwtService.isValid(token)) {
            res.setStatus(401);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"Unauthorized\"}");
            return false;   // ← dừng chuỗi
        }
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest req,
                           HttpServletResponse res,
                           Object handler,
                           ModelAndView mv) {
        // Chạy sau controller — trước render view
        // KHÔNG chạy nếu có exception
    }

    @Override
    public void afterCompletion(HttpServletRequest req,
                                HttpServletResponse res,
                                Object handler,
                                Exception ex) {
        // Chạy sau cùng — kể cả khi có exception
        MDC.clear();
    }
}

// Đăng ký
@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {

    private final AuthInterceptor authInterceptor;
    private final LoggingInterceptor loggingInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loggingInterceptor)
                .addPathPatterns("/**")
                .order(0);

        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/auth/**", "/api/public/**")
                .order(1);
    }
}

Phân tích — Có Interceptor vs Không có Interceptor

❌ Không có Interceptor
  • Phải lặp code check auth ở mọi controller method.
  • Không biết controller method nào sắp chạy để log chi tiết.
  • Không inject được Service vào tầng check (Filter khó hơn).
  • Không có postHandle để modify response sau controller.
  • Không truy cập @RequestMapping metadata.
✅ Có Interceptor
  • Biết controller method sắp chạy — qua Object handler.
  • Inject bean dễ dàng — vì Interceptor là Spring bean.
  • Đọc được annotation của method (như @PublicApi, @AdminOnly).
  • Log chi tiết theo controller — biết endpoint nào chậm.
  • Có postHandle để thêm header sau khi controller xử lý.

Ưu điểm Interceptor so với Filter

  • Biết handler method: handler instanceof HandlerMethod → cast → getMethodAnnotation().
  • Spring DI đầy đủ: inject service, repo, config dễ dàng.
  • Đọc annotation: ví dụ check @PublicApi trên method để skip auth.
  • 3 hook point: preHandle, postHandle, afterCompletion.
  • Được gọi trước/sau render view.

PART 3: AOP — Tầng Method

Định nghĩa

AOP (Aspect-Oriented Programming) là cơ chế của Spring Core — chặn method call, không có khái niệm HTTP. Nó chạy quanh bất kỳ method nào — bất kỳ class nào.

AspectJ — Annotation style
@Aspect
@Component
public class LoggingAspect {

    @Around("@annotation(Loggable)")
    public Object log(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return pjp.proceed();
        } finally {
            long duration = System.currentTimeMillis() - start;
            log.info("{}.{} took {}ms",
                     pjp.getSignature().getDeclaringTypeName(),
                     pjp.getSignature().getName(),
                     duration);
        }
    }
}

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Loggable { }

// Sử dụng
@Service
public class UserService {
    @Loggable
    public UserDto findById(Long id) { ... }
}

Bản chất — Proxy mechanism

Spring AOP dùng proxy — không chặn bytecode như AspectJ. Khi bạn gọi userService.findById(), thực chất là gọi proxy trước:

Bước 1: Thêm dependency:

@Aspect
@Component

    @Around("@annotation(Measured)")
    public Object measure(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed();
        } finally {
            long duration = (System.nanoTime() - start) / 1_000_000;
            log.info("{} — {}ms",
                     pjp.getSignature().toShortString(),
                     duration);
        }

    // Pointcut theo package
    @Before("execution(* com.example.service.*.*(..))")
    public void beforeService(JoinPoint jp) {
        log.debug("Calling: {}", jp.getSignature().toShortString());
    }
}

Phân tích — Có AOP vs Không có AOP

❌ Không có AOP
  • Phải viết try-catch-begin-commit trong mọi service method.
  • Log thời gian chạy lặp ở 50 method.
  • Check quyền ở từng method thủ công.
  • Cache logic lặp đi lặp lại.
  • Code business bị "ô nhiễm" bởi cross-cutting concerns.
✅ Có AOP
  • @Transactional — 1 annotation = transaction.
  • @Cacheable — tự động cache.
  • @Loggable — tự log.
  • @PreAuthorize — security.
  • @Retryable — retry.
  • Business code sạch — chỉ còn logic thật.

Hạn chế của AOP

  • Không có HTTP context — không biết request/response.
  • Self-invocation không chạy — gọi method trong cùng class không qua proxy.
  • Chỉ chặn được public method (với proxy-based AOP).
  • Performance overhead — mỗi method call qua proxy. Ít nhưng có.

Case study thực tế — Chặn user không có quyền

Nếu dùng Filter:

@Component
public class AuthFilter implements Filter {
    public void doFilter(...) {
        String token = extractToken(req);
        if (!isValid(token)) {
            res.setStatus(401);
            return;   // ← chặn
        }
        chain.doFilter(req, res);
    }
}

Vấn đề: AuthFilter chặn cả /api/public/** — không phân biệt endpoint. Muốn exclude phải config URL pattern.

Nếu dùng Interceptor:

@Component
public class AuthInterceptor implements HandlerInterceptor {
    public boolean preHandle(req, res, Object handler) {
        HandlerMethod hm = (HandlerMethod) handler;
        
        // Đọc annotation trên method
        PublicApi pub = hm.getMethodAnnotation(PublicApi.class);
        if (pub != null) return true;   // ← endpoint public → skip
        
        // Check token
        if (!isValid(req)) {
            res.setStatus(401);
            return false;
        }
        return true;
    }
}

// Controller
@GetMapping("/health")
@PublicApi                     // ← đánh dấu public
public String health() { return "OK"; }

Ưu điểm: Interceptor biết được annotation trên method → logic linh hoạt hơn nhiều.

Case study — Transaction + Retry + Cache

Đây là lĩnh vực độc quyền của AOP — Filter và Interceptor không làm được:

@Service
public class PaymentService {

    @Transactional           // ← AOP: transaction
    @Retryable(maxAttempts = 3)   // ← AOP: retry
    @Cacheable("payments")   // ← AOP: cache
    @Loggable                // ← AOP: custom log
    @PreAuthorize("hasRole('ADMIN')")   // ← AOP: security
    public Payment process(Long orderId) { ... }
}

5 concern = 5 aspect chạy quanh 1 method. Filter/Interceptor không làm được vì không có khái niệm "method".

Analogy tổng hợp

Filter = Cổng bảo vệ tòa nhà. Kiểm tra mọi người vào — không quan tâm đến phòng nào. Chặn ở tầng ngoài cùng.

Interceptor = Lễ tân tầng. Biết bạn đến gặp ai (controller), biết phòng nào. Có thể chặn bạn ở tầng — trước khi bạn vào phòng.

AOP = Trợ lý cá nhân. Đi theo bạn vào từng cuộc họp (method). Ghi chú, mở cửa, tắt đèn — quanh từng cuộc họp. Không quan tâm tòa nhà hay tầng.

Có thể dùng cả 3 cùng lúc không?

Có — và thực tế thường vậy:

Filter:         CharacterEncodingFilter, CorsFilter, SpringSecurityFilterChain
                  → xử lý UTF-8, CORS, security toàn cục

Interceptor:    RequestIdInterceptor, AuthInterceptor
                  → thêm request ID, kiểm tra token, log theo endpoint

AOP:            @Transactional, @Cacheable, @Loggable
                  → transaction, cache, business logging
Nguyên tắc chọn:
• Cần HTTP context thô, trước Spring → Filter
• Cần biết controller, đọc annotation method → Interceptor
• Cần chặn method call, không cần HTTP → AOP
Câu hỏi tổng hợp: "Em phân biệt Filter, Interceptor, AOP thế nào?"
Trả lời:
  • Filter: tầng Servlet Container, chạy trước DispatcherServlet, không biết controller. Dùng cho encoding, CORS, security toàn cục.
  • Interceptor: tầng Spring MVC, chạy trong DispatcherServlet, biết handler method. Có 3 hook: preHandle, postHandle, afterCompletion. Dùng cho auth, rate limit, log chi tiết.
  • AOP: tầng method, chạy quanh method call qua proxy. Không có HTTP context. Dùng cho @Transactional, @Cacheable, @Retryable.
Thứ tự chạy: Filter → DispatcherServlet → Interceptor → AOP → Controller → Return Value → Interceptor → Filter → Client.

12. Async Request — Callable, DeferredResult

Vấn đề với sync request

Trong Spring MVC truyền thống: 1 request = 1 thread xử lý đến hết. Nếu method chậm (gọi external API 5s) → thread bị block 5s → không phục vụ request khác.

Tomcat thread pool: 200 threads Request 1 → Thread 1 ────┐ Request 2 → Thread 2 ────┤ Đều gọi external API chậm 5s Request 3 → Thread 3 ────┤ → Cả 3 thread bị block ... │ Request 200 → Thread 200─┘ Request 201 → WAITING — hết thread!

Servlet 3.0 Async — Giải pháp

Servlet 3.0 (2009) cho phép trả thread về pool ngay khi bắt đầu xử lý async. Kết quả trả về sau — không giữ thread.

Spring MVC — 3 cách async

Cách 1: Callable<T>

@GetMapping("/users/{id}")
public Callable<UserDto> get(@PathVariable Long id) {
    return () -> {
        // Chạy trên thread khác — không giữ Tomcat thread
        Thread.sleep(5000);
        return userService.findById(id);
    };
}

Spring chạy Callable trên TaskExecutor. Tomcat thread được release ngay.

Cách 2: DeferredResult<T>

@GetMapping("/notify")
public DeferredResult<String> waitForEvent() {
    DeferredResult<String> result = new DeferredResult<>(30_000L);   // timeout 30s

    // Đăng ký callback vào event bus
    eventBus.subscribe(event -> result.setResult(event.getMessage()));

    // Timeout handler
    result.onTimeout(() -> result.setErrorResult("timeout"));

    return result;   // return ngay — thread release
}

// Từ thread khác:
void onExternalEvent(String msg) {
    pendingResults.forEach(r -> r.setResult(msg));
}

Dùng cho long polling — client chờ event từ server.

Cách 3: WebAsyncTask

@GetMapping("/users/{id}")
public WebAsyncTask<UserDto> get(@PathVariable Long id) {
    Callable<UserDto> task = () -> userService.findById(id);
    WebAsyncTask<UserDto> async = new WebAsyncTask<>(5000L, task);

    async.onTimeout(() -> {
        throw new TimeoutException("Too slow");
    });

    async.onCompletion(() -> {
        log.info("Done");
    });

    return async;
}

Debug Dễ Khó (stack trace tách rời)
Dùng khi Method nhanh (< 100ms) Gọi external chậm, long polling

WebFlux vs MVC

WebFlux — reactive stack, chạy trên Netty, event loop, không block thread. Khác biệt cơ bản:

Spring MVCSpring WebFlux
Thread model1 thread/requestEvent loop (vài thread)
BackpressureKhôngCó (Reactive Streams)

ServerTomcat/JettyNetty
Khi nào dùngCRUD, blocking codeHigh concurrency, streaming
Đừng chọn WebFlux chỉ vì "trend". Nếu code có JDBC, JPA (blocking) → WebFlux không giải quyết được gì, chỉ tăng complexity. Chỉ dùng WebFlux khi toàn bộ stack reactive.
Câu hỏi: "Khi nào dùng Callable thay vì return trực tiếp?"
Trả lời: Khi method cần gọi external service chậm (API, DB, file) — giữ thread Tomcat trong 5s làm lãng phí. Callable trả thread về pool ngay, chạy logic trên thread khác, nhờ đó tăng throughput. Không nên dùng cho method nhanh — overhead không cần thiết.

14. Cấu hình MVC trong Spring Boot

WebMvcAutoConfiguration — Cái gì auto-config?

Khi bạn thêm spring-boot-starter-web, Spring Boot tự config:

  • DispatcherServlet + mapping /.
  • RequestMappingHandlerMapping, RequestMappingHandlerAdapter.
  • HttpMessageConverter mặc định (Jackson, String, ByteArray...).
  • ViewResolver cho template engine trên classpath.
  • HandlerExceptionResolver chain.
  • Static resources handler (/static, /public...).
  • Default error page (/error).

WebMvcConfigurer — Custom MVC

Interface chính để custom MVC mà không tắt auto-config:

@Configuration
public class WebConfig implements WebMvcConfigurer {

    // Thêm interceptor
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoggingInterceptor())
                .addPathPatterns("/api/**");
    }

    // Thêm argument resolver
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new CurrentUserResolver());
    }

    // Thêm message converter
    @Override
    public void extendMessageConverters(List<HttpMessageConverter<?>> converters) {
        converters.add(new YamlHttpMessageConverter());
    }

    // CORS
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://myapp.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE");
    }

    // Static resources
    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/files/**")
                .addResourceLocations("file:uploads/");
    }

    // Formatter
    @Override
    public void addFormatters(FormatterRegistry registry) {
        registry.addFormatter(new DateFormatter("dd/MM/yyyy"));
    }
}

@EnableWebMvc — Khi nào dùng?

@EnableWebMvc = import DelegatingWebMvcConfiguration — tắt toàn bộ auto-config MVC của Spring Boot.

Hầu như không bao giờ dùng @EnableWebMvc trong Spring Boot. Nó tắt auto-config → mất static resources, mất Jackson, mất message converter mặc định → bạn phải config lại hết.

Chỉ dùng khi: bạn muốn toàn quyền kiểm soát, hoặc dùng Spring thuần (không Boot).

15. Best Practices + Checklist + Interview tổng hợp

✅ Best Practices Controller

  • Controller mỏng — chỉ nhận request, gọi service, trả response. Không business logic.
  • Dùng DTO — không expose entity.
  • @RestController — cho API JSON.
  • @ResponseEntity khi cần status/header động.
  • @Valid để validate request.
  • @RestControllerAdvice cho xử lý exception tập trung.
  • Constructor injection — không field injection.
  • Không @Transactional trên controller — để ở service.
  • Version API: /api/v1/users.
  • Đúng HTTP status: 201 cho create, 204 cho delete, 404 cho not found.

❌ Anti-patterns

  • Fat controller — logic trộn trong controller.
  • Expose entity — lộ DB schema, dễ vòng lặp JSON.
  • Try-catch trong controller — dùng @ExceptionHandler.
  • Field injection trong controller.
  • Response lỗi không thống nhất — mỗi nơi 1 format.
  • Trả 200 cho mọi case — không dùng HTTP status.
  • Business logic trong Filter/Interceptor — không phải chỗ của nó.
