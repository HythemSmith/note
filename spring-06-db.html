1. JDBC — Nền tảng (giới thiệu)

JDBC là gì?

JDBC (Java Database Connectivity) là API chuẩn của Java để kết nối và thao tác với database quan hệ. Ra đời từ JDK 1.1, đến nay vẫn là nền tảng của mọi thư viện data access trong Java.

JDBC gồm 4 thành phần chính:

  • Driver: implementation cụ thể cho từng DB (MySQL Connector/J, PostgreSQL JDBC).
  • Connection: kết nối đến DB — được quản lý bởi DriverManager hoặc DataSource.
  • Statement / PreparedStatement: câu lệnh SQL để thực thi.
  • ResultSet: kết quả trả về — con trỏ duyệt từng row.

Ví dụ JDBC thuần

public User findById(Long id) throws SQLException {
    String sql = "SELECT id, name, email FROM users WHERE id = ?";

    try (Connection conn = DriverManager.getConnection(URL, USER, PASS);
         PreparedStatement ps = conn.prepareStatement(sql)) {

        ps.setLong(1, id);

        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) {
                User u = new User();
                u.setId(rs.getLong("id"));
                u.setName(rs.getString("name"));
                u.setEmail(rs.getString("email"));
                return u;
            }
            return null;
        }
    }
}

7 vấn đề của JDBC thuần

  1. Boilerplate khủng khiếp: getConnection, try-catch-finally, close... lặp đi lặp lại.
  2. Dễ SQL Injection nếu dùng Statement thay vì PreparedStatement.
  3. Phải tự map ResultSet → object — thủ công, dễ sai.
  4. Không có transaction management — tự commit/rollback.
  5. Không có connection pool — tạo connection mỗi lần → chậm 50-100ms.
  6. Không có caching — mỗi query đều chạm DB.
  7. Không portable — đổi DB → phải sửa SQL (dialect khác).

Câu hỏi: "PreparedStatement khác Statement thế nào?"
Trả lời: PreparedStatement pre-compile SQL ở DB → chống SQL Injection, nhanh hơn khi gọi nhiều lần cùng query. Statement nối chuỗi SQL → dễ bị injection.

2. Spring JDBC — JdbcTemplate (giới thiệu)

Spring giải quyết vấn đề gì?

JdbcTemplate là wrapper của Spring quanh JDBC — lo hết boilerplate, để bạn chỉ tập trung viết SQL và map kết quả.

JDBC thuần — 20 dòng
Connection conn = null;
PreparedStatement ps = null;
ResultSet rs = null;
try {
    conn = dataSource.getConnection();
    ps = conn.prepareStatement(sql);
    ps.setLong(1, id);
    rs = ps.executeQuery();
    if (rs.next()) {
        User u = new User();
        u.setId(rs.getLong("id"));
        u.setName(rs.getString("name"));
        return u;
    }
    return null;
} catch (SQLException e) {
    throw new DataAccessException(e);
} finally {
    if (rs != null) rs.close();
    if (ps != null) ps.close();
    if (conn != null) conn.close();
}
JdbcTemplate — 3 dòng
return jdbcTemplate.queryForObject(
    "SELECT * FROM users WHERE id = ?",
    userRowMapper,
    id
);

Spring tự lấy connection, set param, đóng resource, chuyển exception.

Các method chính

// Query 1 object
User u = jdbc.queryForObject("SELECT * FROM users WHERE id = ?", rowMapper, 1L);

// Query list
List<User> users = jdbc.query("SELECT * FROM users WHERE status = ?", rowMapper, "ACTIVE");

// Update
int rows = jdbc.update("UPDATE users SET name = ? WHERE id = ?", "Bob", 1L);

// Batch update — insert 1000 row hiệu quả
jdbc.batchUpdate("INSERT INTO users (name) VALUES (?)",
    users.stream().map(u -> new Object[]{u.getName()}).toList());

// NamedParameterJdbcTemplate — dùng :param
Map<String, Object> params = Map.of("id", 1L, "status", "ACTIVE");
namedJdbc.queryForObject(
    "SELECT * FROM users WHERE id = :id AND status = :status",
    params, rowMapper);

RowMapper — map ResultSet → object

public class UserRowMapper implements RowMapper<User> {
    @Override
    public User mapRow(ResultSet rs, int rowNum) throws SQLException {
        User u = new User();
        u.setId(rs.getLong("id"));
        u.setName(rs.getString("name"));
        u.setEmail(rs.getString("email"));
        return u;
    }
}

Khi nào dùng JdbcTemplate?

  • Query phức tạp cần SQL cụ thể (window function, CTE, hint).
  • Báo cáo, thống kê — không cần entity, chỉ cần data.
  • Bulk operation hiệu năng cao — insert/update hàng loạt.
  • Stored procedure phức tạp.
  • Legacy DB không hỗ trợ JPA tốt.
Câu hỏi: "Khi nào dùng JdbcTemplate thay vì JPA?"
Trả lời: Khi cần query phức tạp, bulk operation, báo cáo thống kê, hoặc làm việc với legacy DB. JPA tốt cho CRUD, quan hệ phức tạp; JdbcTemplate tốt cho performance-critical và query không theo entity.

3. Connection Pool — HikariCP (giới thiệu)

Vấn đề

Mở 1 connection đến DB tốn 50-100ms (TCP handshake + auth + session init). Nếu mỗi query đều mở connection mới → app cực chậm.

Connection Pool là gì?

Connection Pool = giữ sẵn N connection, tái sử dụng. App mượn 1 connection, dùng xong trả lại pool thay vì đóng.

┌────────────────────────────────────────────────┐ │ CONNECTION POOL (HikariCP) │ │ │ │ [conn1] [conn2] [conn3] ... [conn10] │ │ ↑ ↑ ↑ │ │ │ │ │ │ │ └──────┴──────┴─ App mượn/trả │ │ │ │ maximum-pool-size: 10 │ │ minimum-idle: 5 │ └────────────────────────────────────────────────┘ │ ▼ ┌──────────┐ │ Database │ └──────────┘

HikariCP — Pool mặc định Spring Boot 2+

  • Nhanh nhất trong các pool Java hiện nay.
  • Nhẹ — bytecode nhỏ, ít dependency.
  • Không lock contention — dùng lock-free design.

Cấu hình

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: secret
    hikari:
      maximum-pool-size: 10       # tối đa 10 connection
      minimum-idle: 5             # giữ ít nhất 5 sẵn
      connection-timeout: 30000   # chờ pool 30s
      idle-timeout: 600000        # đóng idle 10 phút
      max-lifetime: 1800000       # connection sống 30 phút
      pool-name: MyHikariPool

Công thức chọn pool size

connections = ((core_count × 2) + effective_spindle_count)

Ví dụ: 4 core, 1 SSD → khoảng 9-10 connection. Không phải càng lớn càng tốt — nhiều connection = nhiều context switch, DB lock contention.

Monitoring

# application.yml
management.endpoints.web.exposure.include: health,metrics
# → /actuator/metrics/hikaricp.connections.active
# → /actuator/metrics/hikaricp.connections.pending
Connection leak: nếu app quên trả connection (không close), pool cạn dần → app treo. HikariCP có leak-detection-threshold để log cảnh báo.
Câu hỏi: "Công thức chọn pool size?"
Trả lời: core_count × 2 + spindle_count. Không phải càng lớn càng tốt — nhiều connection = nhiều context switch, DB lock. Ví dụ 4 core, 1 SSD → 9-10 connection.

4. JPA vs Hibernate vs Spring Data JPA

Bức tranh phân tầng

┌──────────────────────────────────────────────────────┐ │ Tầng 4: Spring Data JPA │ │ (Repository interface, query method, @Query) │ ├──────────────────────────────────────────────────────┤ │ Tầng 3: JPA (specification) + Hibernate (impl) │ │ (@Entity, EntityManager, JPQL, Persistence Context) │ ├──────────────────────────────────────────────────────┤ │ Tầng 2: Spring JDBC (JdbcTemplate) │ ├──────────────────────────────────────────────────────┤ │ Tầng 1: JDBC (Java API) │ │ (Connection, PreparedStatement, ResultSet) │ ├──────────────────────────────────────────────────────┤ │ Tầng 0: JDBC Driver (MySQL, PostgreSQL...) │ └──────────────────────────────────────────────────────┘

JPA là gì?

JPA (Java Persistence API) là specification — chuẩn định nghĩa cách map object Java ↔ bảng DB. Nó KHÔNG PHẢI implementation.

JPA định nghĩa:

  • Annotation: @Entity, @Table, @Id, @Column...
  • Interface: EntityManager, Query, TypedQuery...
  • Ngôn ngữ: JPQL (Java Persistence Query Language).
  • Vòng đời entity, persistence context, transaction integration.

Hibernate là gì?

Hibernate là implementation phổ biến nhất của JPA. Ngoài việc implement đầy đủ JPA, Hibernate còn có API riêng (Session, Criteria, HQL).

Các implementation khác của JPA: EclipseLink (reference impl), OpenJPA, DataNucleus.

Spring Data JPA là gì?

Spring Data JPA là lớp abstraction trên JPA — giúp bạn không phải viết code boilerplate khi dùng EntityManager.

JPA thuần — phải viết nhiều
@Repository
public class UserRepositoryImpl {

    @PersistenceContext
    private EntityManager em;

    public User save(User u) {
        if (u.getId() == null) {
            em.persist(u);
            return u;
        }
        return em.merge(u);
    }

    public Optional<User> findById(Long id) {
        User u = em.find(User.class, id);
        return Optional.ofNullable(u);
    }

    public List<User> findAll() {
        return em.createQuery("SELECT u FROM User u", User.class)
                 .getResultList();
    }
}
Spring Data JPA — 1 interface
public interface UserRepository
        extends JpaRepository<User, Long> {
    // save, findById, findAll, delete...
    // Tất cả được sinh tự động!
}

Spring Data JPA tự sinh implementation dựa trên interface.

Bảng so sánh

JPA Hibernate Spring Data JPA
Loại Specification Implementation Abstraction trên JPA
Cần viết code? Nhiều (EntityManager) Nhiều (Session) Ít (chỉ interface)
Portable? ✅ Đổi impl được ⚠️ Gắn Hibernate ✅ Portability kế thừa JPA
Dùng khi — — 99% dự án Spring
Trong Spring Boot, bạn hầu như chỉ dùng Spring Data JPA — nhưng bên dưới vẫn là Hibernate (default) implement JPA spec. Hiểu Hibernate = hiểu cách Spring Data JPA hoạt động.
Câu hỏi: "JPA và Hibernate khác gì?"
Trả lời: JPA là specification (chuẩn) — định nghĩa annotation, interface, ngôn ngữ query. Hibernate là implementation cụ thể của JPA. Giống như Servlet là spec, Tomcat là implementation. Spring Data JPA là abstraction trên JPA, giúp giảm boilerplate.

5. ⭐ Entity Lifecycle & Persistence Context

Đây là khái niệm quan trọng nhất của JPA. Hiểu nó = hiểu tại sao JPA hoạt động như nó hoạt động.

Persistence Context là gì?

Persistence Context là một "cache tầng 1" của EntityManager — chứa tất cả entity đang được quản lý trong 1 transaction.

Tưởng tượng Persistence Context như một "bảng trắng" trên bàn làm việc. Khi bạn load entity từ DB, nó được ghi lên bảng trắng. Trong suốt transaction, bạn thao tác trên bảng trắng. Khi commit, Hibernate so sánh bảng trắng với DB và ghi các thay đổi xuống.

Sơ đồ Persistence Context

┌────────────────────────────────────────────────────────────┐ │ ENTITY MANAGER (Persistence Context) │ │ │ │ ┌────────────────────────────────────────────────────┐ │ │ │ Managed Entities (đang được quản lý) │ │ │ │ │ │ │ │ User(id=1, name="Alice") │ │ │ │ ├─ Snapshot: {name: "Alice"} ← copy gốc │ │ │ │ └─ Current: {name: "Alice"} │ │ │ │ │ │ │ │ Order(id=100, status="PENDING") │ │ │ │ ├─ Snapshot: {status: "PENDING"} │ │ │ │ └─ Current: {status: "DONE"} ← đã đổi │ │ │ │ │ │ │ └────────────────────────────────────────────────────┘ │ │ │ │ Khi flush/commit: │ │ So sánh Current vs Snapshot │ │ Nếu khác → sinh UPDATE │ └────────────────────────────────────────────────────────────┘

Dirty Checking — Trái tim của JPA

Dirty Checking là cơ chế Hibernate tự phát hiện entity đã thay đổi và sinh câu UPDATE khi flush — bạn không cần gọi save().

@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository repo;

    @Transactional
    public void changeName(Long id, String newName) {
        User user = repo.findById(id).orElseThrow();
        user.setName(newName);
        // ← KHÔNG gọi repo.save()
        // Khi transaction commit → Hibernate tự sinh UPDATE
    }
}

SQL log:

-- Khi findById: SELECT id, name, email FROM users WHERE id = 1 -- Khi commit (dirty checking phát hiện name đã đổi): UPDATE users SET name = 'Bob', email = 'a@b.com' WHERE id = 1

Cơ chế hoạt động của Dirty Checking

1. Load User từ DB ├─ Hibernate load row → tạo object ├─ Lưu snapshot: {name: "Alice", email: "a@b.com"} └─ Đặt object vào Persistence Context 2. Bạn đổi name └─ user.setName("Bob") └─ Object trong PC giờ là {name: "Bob", email: "a@b.com"} └─ Snapshot vẫn là {name: "Alice", ...} 3. Khi flush/commit ├─ Hibernate duyệt mọi managed entity ├─ So sánh Current vs Snapshot ├─ Nếu khác → sinh UPDATE với các field khác └─ Execute SQL 4. Kết quả └─ DB đã update — bạn không cần gọi save()

Identity Map — 1 row = 1 object

Trong 1 persistence context, mỗi row trong DB chỉ map đến đúng 1 object. Đây là Identity Map pattern.

@Transactional
public void demo() {
    User u1 = em.find(User.class, 1L);   // ← SELECT
    User u2 = em.find(User.class, 1L);   // ← KHÔNG query lại

    System.out.println(u1 == u2);   // true — cùng object!
}

Lợi ích: tránh load trùng, đảm bảo consistency trong transaction.

Flush vs Commit

Flush Commit
Làm gì Ghi thay đổi xuống DB (SQL chạy) Xác nhận transaction vĩnh viễn
Rollback được? ✅ Có — chưa commit ❌ Không — đã vĩnh viễn
Tự động? Trước query, trước commit Khi transaction kết thúc

4 loại FlushMode

  • AUTO (mặc định): flush trước query liên quan entity đã thay đổi.
  • COMMIT: chỉ flush khi commit — dùng khi query không liên quan.
  • MANUAL: chỉ flush khi gọi em.flush() — dùng trong batch.
  • ALWAYS: flush trước mọi query — chậm nhất.
Đào sâu — Tại sao auto flush trước query? Giả sử bạn đổi user.name = "Bob", rồi chạy SELECT u WHERE u.name = 'Bob'. Nếu không flush trước, Hibernate sẽ không thấy user trong DB (vì chưa update) → kết quả thiếu. Flush trước query đảm bảo consistency.
Câu hỏi: "Persistence context là gì? Dirty checking hoạt động thế nào?"
Trả lời: Persistence Context là cache tầng 1 của EntityManager — chứa mọi managed entity trong transaction. Dirty checking hoạt động bằng cách: khi load entity, Hibernate lưu 1 snapshot. Khi flush, so sánh current object vs snapshot → nếu khác → sinh UPDATE. Nhờ đó không cần gọi save().

6. Mapping cơ bản — @Entity, @Column, @Id

Entity tối thiểu

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 100)
    private String name;

    @Column(unique = true, nullable = false)
    private String email;

    @Enumerated(EnumType.STRING)
    private Status status;

    @Temporal(TemporalType.TIMESTAMP)
    private Date createdAt;

    @Transient
    private String temporaryData;   // ← không map vào DB

    // getter/setter
}

Khuyến nghị chọn strategy

@Id

    generator = "user_seq")

    sequenceName = "users_id_seq",
    allocationSize = 50)

allocationSize=50 → lấy 50 ID 1 lần, giảm round-trip.

MySQL → IDENTITY (chấp nhận)

@GeneratedValue(strategy = GenerationType.IDENTITY)

MySQL không có sequence thật → dùng IDENTITY.

@Embedded — Nhúng value object

@Embeddable
public class Address {
    private String street;
    private String city;
    private String zipCode;
}

@Entity
public class User {
    @Id @GeneratedValue Long id;

    @Embedded
    private Address address;

}
Không dùng Lombok @Data cho entity. Vì @Data sinh equals/hashCode dựa trên mọi field → dễ gây bug với lazy loading và trong HashSet/HashMap. Chỉ dùng @Getter/@Setter.
Câu hỏi: "Chiến lược sinh ID nào tốt nhất?"
Trả lời: SEQUENCE với allocationSize lớn (như 50) là tốt nhất cho PostgreSQL/Oracle — hỗ trợ batch insert. MySQL không có sequence → dùng IDENTITY (không hỗ trợ batch insert nhưng chấp nhận được). Tránh TABLE vì chậm.

7. Mapping quan hệ — @OneToMany, @ManyToOne, @ManyToMany

4 loại quan hệ

AnnotationQuan hệVí dụ
@ManyToOneNhiều con → 1 chaOrder → User
@OneToMany1 cha → nhiều conUser → Orders
@OneToOne1-1User → Profile
@ManyToManyN-N (qua bảng trung gian)User ↔ Roles

Ví dụ User ↔ Order

@Entity
public class User {

    @Id @GeneratedValue Long id;
    private String name;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();
}

@Entity
@Table(name = "orders")
public class Order {

    @Id @GeneratedValue Long id;
    private BigDecimal total;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;
}

Sơ đồ quan hệ

USER (1) ORDER (N) ┌────────────┐ ┌──────────────────┐ │ id (PK) │◄─────────────│ user_id (FK) │ │ name │ │ id (PK) │ └────────────┘ │ total │ └──────────────────┘ Owner side (quản lý FK) = Order (bên @ManyToOne) Inverse side = User (bên @OneToMany có mappedBy)

Owner side vs Inverse side

Owner side = bên sở hữu foreign key = bên có @JoinColumn = bên @ManyToOne.

Inverse side = bên có mappedBy = bên @OneToMany.

Quy tắc quan trọng: Khi bạn muốn tạo quan hệ, phải set FK ở owner side:

// ❌ SAI — chỉ set ở inverse side
User user = new User();
Order order = new Order();
user.getOrders().add(order);   // ← không có tác dụng với DB!

// ✅ ĐÚNG — set cả 2 để consistent trong memory
user.getOrders().add(order);
order.setUser(user);           // ← FK thực sự được ghi

// Cha vẫn tồn tại

@ManyToMany — Ít dùng

@Entity
public class User {
    @ManyToMany
    @JoinTable(
        name = "user_roles",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id")
    )
    private Set<Role> roles = new HashSet<>();
}

Tại sao ít dùng?

  • Không kiểm soát được bảng trung gian (không thêm field được).
  • Cascade phức tạp — dễ xóa nhầm.
  • Performance kém khi số lượng lớn.

Thay thế: tạo entity trung gian UserRole với @ManyToOne đến cả 2 bên.

Best practice:
  • Luôn @ManyToOne(fetch = LAZY).
  • Luôn set FK ở owner side.
  • Cẩn thận cascade — chỉ dùng cho quan hệ cha-con thực sự.
  • Tránh @ManyToMany — tạo entity trung gian.
Câu hỏi: "mappedBy là gì? Owner side là bên nào?"
Trả lời: mappedBy chỉ ra bên nào KHÔNG sở hữu FK — luôn đặt ở phía @OneToMany. Owner side là bên có @ManyToOne + @JoinColumn — bên thực sự ghi FK xuống DB. Khi tạo quan hệ phải set FK ở owner side, nếu không thì DB không lưu.

8. ⭐ FetchType LAZY vs EAGER — Chi tiết

Khái niệm

FetchType quyết định khi nào Hibernate load dữ liệu của quan hệ:

  • LAZY: load khi bạn truy cập vào field đó.
  • EAGER: load ngay lập tức khi load entity cha.

Giá trị mặc định — Gây bất ngờ

Quan hệMặc định
@OneToManyLAZY
@ManyToManyLAZY
@ManyToOneEAGER ⚠️
@OneToOneEAGER ⚠️
@ManyToOne mặc định EAGER là vấn đề lớn trong nhiều dự án. Mỗi lần load entity con, cha cũng bị load theo → N+1 tiềm ẩn.

Sơ đồ EAGER vs LAZY

EAGER — Load ngay: User u = userRepo.findById(1L) │ ├─ SELECT * FROM users WHERE id = 1 │ ├─ Ngay lập tức: │ SELECT * FROM orders WHERE user_id = 1 │ SELECT * FROM roles WHERE user_id = 1 │ SELECT * FROM profiles WHERE user_id = 1 │ ... (mọi quan hệ EAGER) │ └─ Return User với mọi field đã load LAZY — Load khi cần: User u = userRepo.findById(1L) │ ├─ SELECT * FROM users WHERE id = 1 │ └─ Return User, các quan hệ là PROXY (chưa load) Khi bạn gọi: u.getOrders().size() │ └─ Lúc này mới load: SELECT * FROM orders WHERE user_id = 1

Cơ chế proxy của LAZY

Khi Hibernate load entity cha có quan hệ LAZY, nó tạo proxy object — subclass của entity thật — chưa có data.

User (real object) ├─ id: 1 ├─ name: "Alice" └─ orders: ProxyOrderList ← Đây là proxy ├─ Không chứa data thật ├─ Giữ reference đến Session └─ Khi truy cập → query DB Khi bạn gọi u.getOrders(): ├─ Nếu Session còn mở: │ └─ Query DB → load thật └─ Nếu Session đã đóng: └─ LazyInitializationException ❌

Ví dụ code — Thấy rõ sự khác biệt

@Entity
public class User {
    @Id @GeneratedValue Long id;
    private String name;

    @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
    private List<Order> orders = new ArrayList<>();

    @ManyToOne(fetch = FetchType.LAZY)   // ← override mặc định EAGER
    @JoinColumn(name = "team_id")
    private Team team;
}

SQL log — So sánh EAGER vs LAZY

EAGER — Load thừa
-- User.team là EAGER (mặc định @ManyToOne) SELECT u.* FROM users u WHERE u.id = 1 -- Hibernate tự load Team theo SELECT t.* FROM teams t WHERE t.id = 5 // 2 query — kể cả khi không cần Team
LAZY — Chỉ load khi cần
-- User.team là LAZY SELECT u.* FROM users u WHERE u.id = 1 // 1 query — nếu không truy cập team -- Khi gọi u.getTeam().getName(): SELECT t.* FROM teams t WHERE t.id = 5

Khi bạn truy cập field LAZY ngoài transaction → exception.

Ví dụ bug:

Spring giữ Session mở suốt request → lazy load ngoài service vẫn hoạt động. Nhưng:

  • Giữ connection DB lâu → cạn pool.
  • Che giấu N+1 — query xảy ra ở tầng view.
  • Không kiểm soát được transaction boundary.
Spring Boot 3.x khuyến nghị tắt OSIV: spring.jpa.open-in-view=false. Nhưng nếu tắt, phải fix LazyInitializationException bằng 1 trong 3 cách trên.

Bảng so sánh

Fetch Ưu Nhược

EAGER Không lo exception Load thừa, N+1 tiềm ẩn, chậm
Best practice: Mọi quan hệ → LAZY. Khi cần load quan hệ → dùng JOIN FETCH hoặc @EntityGraph. Không bao giờ dùng EAGER cho collection.
Câu hỏi: "LAZY vs EAGER? LazyInitializationException fix thế nào?"
Trả lời: LAZY load khi truy cập, EAGER load ngay. Mặc định: @OneToMany/@ManyToMany = LAZY, @ManyToOne/@OneToOne = EAGER. LazyInitializationException xảy ra khi truy cập field LAZY ngoài transaction → fix bằng JOIN FETCH, @EntityGraph, hoặc DTO projection. Không nên dùng OSIV để che giấu.

9. ⭐ N+1 Query — Case study & Fix chi tiết

Đây là bug performance phổ biến nhất trong JPA. Mình sẽ đi qua 4 case study thực tế.

N+1 là gì?

Khi bạn load N entity cha, rồi truy cập quan hệ con → phát sinh thêm N query (mỗi cha 1 query load con). Tổng = 1 + N.

Case Study 1 — Classic N+1 với @OneToMany

Code có bug

@Service
public class OrderService {

    public List<OrderSummary> getOrderSummaries() {
        List<User> users = userRepo.findAll();   // ← 1 query

        return users.stream()
            .map(u -> new OrderSummary(
                u.getName(),
                u.getOrders().size()      // ← N query (mỗi user 1 query)
            ))
            .toList();
    }
}

SQL log thực tế

-- Query 1: load users SELECT * FROM users ← 1 query -- Query 2..N+1: mỗi user load orders SELECT * FROM orders WHERE user_id = 1 ← N+1 SELECT * FROM orders WHERE user_id = 2 ← N+2 SELECT * FROM orders WHERE user_id = 3 ← N+3 ... SELECT * FROM orders WHERE user_id = 1000 ← N+1000 // Tổng: 1 + 1000 = 1001 query chỉ để lấy count!

Fix 1 — DTO Projection (tốt nhất cho case này)

public record OrderSummary(String userName, long orderCount) { }

public interface UserRepository extends JpaRepository<User, Long> {

    @Query("""
        SELECT new com.example.OrderSummary(u.name, COUNT(o))
        FROM User u LEFT JOIN u.orders o
        GROUP BY u.id, u.name
    """)
    List<OrderSummary> findOrderSummaries();
}

SQL sau khi fix

SELECT u.name, COUNT(o.id) AS cnt FROM users u LEFT JOIN orders o ON u.id = o.user_id GROUP BY u.id, u.name // 1 query duy nhất — từ 1001 → 1!

Case Study 3 — N+1 với nhiều collection (MultipleBagFetchException)

Code có bug

@Entity
public class User {
    @OneToMany(mappedBy = "user")
    private List<Order> orders = new ArrayList<>();

    @OneToMany(mappedBy = "user")
    private List<Address> addresses = new ArrayList<>();
}

// Query cố JOIN FETCH 2 collection
@Query("SELECT u FROM User u JOIN FETCH u.orders JOIN FETCH u.addresses")
List<User> findAllDetail();

Exception xảy ra

org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags

Tại sao?

Khi JOIN 2 collection, kết quả trả về là cartesian product — mỗi order × mỗi address. Với 3 orders và 2 addresses → 6 row cho 1 user. Hibernate không biết dedup thế nào.

Fix 1 — Đổi List thành Set (không phải lúc nào cũng đúng)

@OneToMany(mappedBy = "user")
private Set<Order> orders = new HashSet<>();

@OneToMany(mappedBy = "user")
private Set<Address> addresses = new HashSet<>();

Sau đó JOIN FETCH cả 2 được — nhưng vẫn có cartesian product, chỉ dedup bằng Set.

Fix 2 — @BatchSize (khuyến nghị nhất)

@Entity
public class User {
    @OneToMany(mappedBy = "user")
    @BatchSize(size = 20)
    private List<Order> orders;

    @OneToMany(mappedBy = "user")
    @BatchSize(size = 20)
    private List<Address> addresses;
}

SQL sau khi fix:

SELECT * FROM users ← 1 query SELECT * FROM orders WHERE user_id IN (1..20) ← N/20 SELECT * FROM orders WHERE user_id IN (21..40) ← N/20 SELECT * FROM addresses WHERE user_id IN (1..20) ... // Từ 2001 query → 1 + N/20 + N/20 ≈ 101

Fix 3 — Tách query riêng cho từng collection

// Query 1
List<User> users = userRepo.findAll();

// Query 2 — load hết orders
List<Long> userIds = users.stream().map(User::getId).toList();
List<Order> allOrders = orderRepo.findByUserIdIn(userIds);
// → 1 query với WHERE user_id IN (...)

// Query 3 — load hết addresses
List<Address> allAddresses = addressRepo.findByUserIdIn(userIds);

// Merge trong memory
users.forEach(u -> {
    u.setOrders(allOrders.stream().filter(o -> o.getUser().getId().equals(u.getId())).toList());
    u.setAddresses(allAddresses.stream().filter(a -> a.getUser().getId().equals(u.getId())).toList());
});
Case Study 4 — N+1 trong pagination (bug khó phát hiện)

Code có bug

@Query("SELECT u FROM User u JOIN FETCH u.orders")

Warning của Hibernate

HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory!

Vấn đề

Với pagination, Spring cần LIMIT 10 OFFSET 0. Nhưng khi JOIN FETCH collection, mỗi user có nhiều order → 1 user có thể chiếm nhiều row. Hibernate không thể cắt LIMIT ở SQL — phải load tất cả users rồi cắt trong memory → performance tệ hơn cả N+1.

Fix — 2 query approach

// Query 1: Lấy ID của users với phân trang
@Query("SELECT u.id FROM User u WHERE u.status = :status")
Page<Long> findUserIdsByStatus(@Param("status") Status status, Pageable pageable);

// Query 2: Lấy users kèm orders theo IDs
@Query("SELECT DISTINCT u FROM User u JOIN FETCH u.orders WHERE u.id IN :ids")
List<User> findByIdInWithOrders(@Param("ids") List<Long> ids);
@Service
public class UserService {

    public Page<User> search(Status status, Pageable pageable) {
        Page<Long> idsPage = repo.findUserIdsByStatus(status, pageable);

        List<User> users = repo.findByIdInWithOrders(idsPage.getContent());

        return new PageImpl<>(users, pageable, idsPage.getTotalElements());
    }
}

-- Query 1: pagination IDs SELECT u.id FROM users u WHERE u.status = 'ACTIVE' LIMIT 10 OFFSET 0 -- Query 2: load full data cho 10 ID SELECT DISTINCT u.*, o.* FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE u.id IN (1,2,3,...,10) // 2 query — pagination đúng, không load thừa

• Có phân trang → 2-query approach.
Câu hỏi: "N+1 là gì? Có mấy cách fix?"
Trả lời: N+1 là khi load N entity cha rồi truy cập quan hệ con → phát sinh N query phụ. Fix: (1) JOIN FETCH — 1 query, (2) @EntityGraph — declarative, (3) @BatchSize — batch nhiều ID, (4) DTO Projection — chỉ select field cần, (5) 2-query approach cho pagination. Chọn theo use case: pagination cần 2-query, chỉ count cần projection, nhiều collection cần @BatchSize.

Criteria API — Type-safe 100%

public List<User> search(String name, Status status, Integer minAge) {
    CriteriaBuilder cb = em.getCriteriaBuilder();
    CriteriaQuery<User> cq = cb.createQuery(User.class);
    Root<User> root = cq.from(User.class);

    List<Predicate> preds = new ArrayList<>();
    if (name != null) preds.add(cb.like(root.get("name"), "%" + name + "%"));
    if (status != null) preds.add(cb.equal(root.get("status"), status));
    if (minAge != null) preds.add(cb.ge(root.get("age"), minAge));

    cq.where(preds.toArray(new Predicate[0]));
    cq.orderBy(cb.desc(root.get("createdAt")));

    return em.createQuery(cq).getResultList();
}

Specification — Dynamic query dễ tái sử dụng

public class UserSpecs {

    public static Specification<User> nameLike(String name) {
        return (root, q, cb) -> name == null ? null
            : cb.like(cb.lower(root.get("name")), "%" + name.toLowerCase() + "%");
    }

    public static Specification<User> hasStatus(Status status) {
        return (root, q, cb) -> status == null ? null
            : cb.equal(root.get("status"), status);
    }

    public static Specification<User> createdAfter(LocalDate date) {
        return (root, q, cb) -> date == null ? null
            : cb.greaterThanOrEqualTo(root.get("createdAt"), date.atStartOfDay());
    }
}

// Sử dụng
public Page<User> search(UserFilter filter, Pageable pageable) {
    Specification<User> spec = Specification.where(null)
        .and(UserSpecs.nameLike(filter.getName()))
        .and(UserSpecs.hasStatus(filter.getStatus()))
        .and(UserSpecs.createdAfter(filter.getFromDate()));

    return userRepo.findAll(spec, pageable);
}
Chọn cách nào?
  • Query cố định → JPQL với @Query.
  • Query động với nhiều filter → Specification.
  • Cần function đặc thù DB → Native Query.
  • Muốn type-safe hoàn toàn (refactor không sợ sai) → Criteria/Specification.
Câu hỏi: "JPQL khác Native Query chỗ nào?"
Trả lời: JPQL query trên entity (không phải table), portable across DB, Hibernate dịch sang SQL tương ứng. Native Query là SQL thật, chạy trực tiếp DB, dùng được mọi function đặc thù nhưng không portable. Chọn JPQL khi có thể, Native khi cần function đặc thù hoặc optimize performance.

11. Locking — Optimistic & Pessimistic

Vấn đề concurrency

2 user cùng sửa 1 row → last write wins → mất dữ liệu của người trước.

Time User A User B ──── ──────────────────────────── ──────────────────────────── t1 Đọc: balance = 1000 t2 Đọc: balance = 1000 t3 Sửa: +500 → 1500 t4 Sửa: +300 → 1300 t5 Ghi 1500 ← User A bị mất update của B t6 Ghi 1300 (đè lên 1500)

Optimistic Lock — Giả định ít conflict

Dùng cột version để phát hiện conflict:

@Entity
public class Product {
    @Id @GeneratedValue Long id;
    private int quantity;

    @Version
    private Long version;   // ← cột version trong DB
}

Cơ chế:

-- Khi SELECT: đọc cả version SELECT id, quantity, version FROM products WHERE id = 1 -- → quantity=10, version=5 -- Khi UPDATE: check version UPDATE products SET quantity = 15, version = 6 WHERE id = 1 AND version = 5 -- Nếu version đã đổi (user khác update) → 0 row updated → OptimisticLockException

Khi conflict:

@Transactional
public void updateQuantity(Long id, int delta) {
    Product p = productRepo.findById(id).orElseThrow();
    p.setQuantity(p.getQuantity() + delta);
    // Khi commit → nếu version mismatch → OptimisticLockException
}

Retry khi conflict:

@Retryable(
    retryFor = OptimisticLockingFailureException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 100)
)
@Transactional
public void updateQuantity(Long id, int delta) {
    Product p = productRepo.findById(id).orElseThrow();
    p.setQuantity(p.getQuantity() + delta);
}

Pessimistic Lock — Khóa DB ngay

public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}

SQL:

SELECT * FROM products WHERE id = 1 FOR UPDATE -- Lock row này. Thread khác gọi FOR UPDATE sẽ phải chờ.

Pessimistic lock có thể gây deadlock nếu 2 transaction lock 2 row theo thứ tự ngược nhau. Luôn lock theo thứ tự cố định (ví dụ: theo ID tăng dần).
Câu hỏi: "Optimistic vs Pessimistic lock?"
Trả lời: Optimistic dùng cột version — check khi update, throw exception nếu conflict. Phù hợp khi ít conflict, web app. Pessimistic dùng SELECT FOR UPDATE — khóa row, thread khác chờ. Phù hợp khi conflict cao (bán vé, trừ kho) nhưng có thể deadlock.

12. Caching — L1 và L2

Hai tầng cache

┌──────────────────────────────────────────────────────┐ │ APPLICATION │ │ │ │ ┌────────────────────────────────────────────────┐ │ │ │ L1 Cache (Persistence Context) │ │ │ │ - Scope: 1 EntityManager / 1 transaction │ │ │ │ - Tự động, không tắt được │ │ │ │ - Mất khi transaction kết thúc │ │ │ └────────────────────────────────────────────────┘ │ │ │ │ │ ┌────────────────────▼───────────────────────────┐ │ │ │ L2 Cache (Shared) │ │ │ │ - Scope: toàn app (SessionFactory level) │ │ │ │ - Cần cấu hình │ │ │ │ - Provider: Ehcache, Caffeine, Redis │ │ │ │ - Cross-session → chia sẻ giữa các transaction│ │ │ └────────────────────────────────────────────────┘ │ │ │ │ └───────────────────────┼───────────────────────────────┘ │ ▼ ┌──────────┐ │ Database │ └──────────┘

L1 Cache — Persistence Context

Đã nói ở mục 5 — không cần config, mỗi transaction có 1 Persistence Context riêng.

-- Trong cùng 1 transaction: em.find(User.class, 1L); → SELECT em.find(User.class, 1L); → Cache hit, không query em.find(User.class, 1L); → Cache hit // Chỉ 1 query cho 3 lần find!

L2 Cache — Cấu hình

  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          region:
            factory_class: org.hibernate.cache.jcache.JCacheRegionFactory
        javax:
          cache:
            provider: org.ehcache.jsr107.EhcacheCachingProvider

Trên entity:

@Entity
@Cacheable                        // ← đánh dấu entity được cache L2
@org.hibernate.annotations.Cache(
    usage = CacheConcurrencyStrategy.READ_WRITE
)
public class Product {
    @Id Long id;
    private String name;
    private BigDecimal price;
}

Cache Concurrency Strategy

Strategy Khi nào dùng
READ_ONLY Data không bao giờ thay đổi — nhanh nhất
READ_WRITE Data thay đổi, cần consistent — có lock
NONSTRICT_READ_WRITE Chấp nhận stale tạm thời — nhanh hơn
TRANSACTIONAL Full transactional — chậm, cần JTA

Query Cache — Cache kết quả query

# Bật query cache
hibernate.cache.use_query_cache: true

// Trên query
@QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
@Query("SELECT p FROM Product p WHERE p.category = :cat")
List<Product> findByCategory(@Param("cat") String cat);

L2 Cache hoạt động thế nào?

Transaction 1: em.find(Product.class, 1L) │ ├─ L1 cache miss ├─ L2 cache miss ├─ SELECT FROM products → load ├─ Put vào L1 └─ Put vào L2 │ commit → L1 cleared, L2 giữ Transaction 2 (transaction mới): em.find(Product.class, 1L) │ ├─ L1 cache miss ├─ L2 cache HIT → return object (không query DB) ├─ Put vào L1 └─ Return │ commit
Cache invalidation — vấn đề muôn thuở. Khi update entity, L2 cache của entity đó phải bị invalidate. Hibernate tự làm — nhưng nếu bạn update DB bằng native SQL hoặc thao tác ngoài Hibernate → cache stale.

Khi nào dùng L2?

  • ✅ Data ít thay đổi (categories, countries, config).
  • ✅ Read-heavy, write-rare.
  • ✅ Reference data load nhiều lần.
  • ❌ Data thay đổi liên tục (stock, balance).
  • ❌ Query có filter động.

So sánh L1 vs L2 vs Spring Cache

L1 Cache L2 Cache Spring @Cacheable
Scope Transaction SessionFactory Application
Cần config? Không Có Có
Cache gì Entity Entity + query Method result
Bypass? Không Có (evict) Có
Provider Hibernate Ehcache/Caffeine/Redis Caffeine/Redis
Câu hỏi: "Hibernate L1 vs L2 cache?"
Trả lời: L1 là Persistence Context — scope 1 transaction, tự động, không tắt được. L2 là shared cache — scope toàn app, cần config provider (Ehcache/Caffeine/Redis), chỉ áp dụng cho entity có @Cacheable. L2 cần invalidate khi update — nếu thao tác DB ngoài Hibernate thì cache stale.

Page vs Slice vs List

Type Total count? Query Khi nào dùng
Page<T> ✅ Có (COUNT query) 2 query UI cần hiển thị số trang
Slice<T> ❌ Không 1 query (fetch size+1) Infinite scroll, "Load more"
List<T> ❌ Không 1 query Không cần phân trang
Đào sâu — Tại sao Page chậm hơn Slice? Vì Page cần SELECT COUNT(*) để biết tổng số. Với bảng lớn hoặc JOIN phức tạp, count query có thể chậm hơn cả data query. Slice chỉ fetch N+1 row để biết còn tiếp không.

Trả lời: Page chạy thêm COUNT query để biết tổng số → 2 query. Slice chỉ fetch size+1 để biết còn tiếp không → 1 query. Page dùng cho UI có hiển thị số trang. Slice dùng cho infinite scroll, load more — nhanh hơn.

15. Auditing — @CreatedDate, @LastModifiedDate

Auditing là gì?

Tự động ghi lại thông tin: ai tạo, khi nào tạo, ai sửa, khi nào sửa — không cần set thủ công.

Bật Auditing

@Configuration
@EnableJpaAuditing   // ← bật tính năng
public class JpaConfig { }

Đánh dấu entity

@Entity
@EntityListeners(AuditingEntityListener.class)   // ← bật listener
public class User {

    @Id @GeneratedValue Long id;

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String lastModifiedBy;
}

Cung cấp user hiện tại — AuditorAware

@Component
public class SecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()) {
            return Optional.of("system");
        }
        return Optional.of(auth.getName());
    }
}

Base Entity — Tái sử dụng

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
@Getter @Setter
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String lastModifiedBy;
}

@Entity
public class User extends BaseEntity {
    @Id @GeneratedValue Long id;
    private String name;
}

Soft Delete — Xóa mềm

@Entity
@SQLDelete(sql = "UPDATE users SET deleted = true WHERE id = ?")
@Where(clause = "deleted = false")
public class User {

    @Id @GeneratedValue Long id;
    private boolean deleted = false;
}
  • @SQLDelete: khi gọi delete → chạy UPDATE thay vì DELETE.
  • @Where: mọi query tự thêm WHERE deleted = false.
Với Hibernate 6+, dùng @SQLRestriction thay cho @Where (deprecated).
Câu hỏi: "Làm sao tự động ghi created_at, updated_at?"
Trả lời: Bật @EnableJpaAuditing ở config, thêm @EntityListeners(AuditingEntityListener.class) trên entity, đánh dấu field với @CreatedDate, @LastModifiedDate. Cho audit user → implement AuditorAware để lấy user từ SecurityContext.

16. Best Practices + Checklist

✅ Best Practices — Entity Design

  • Dùng Long cho ID, không dùng int.
  • Không dùng Lombok @Data cho entity — chỉ @Getter/@Setter.
  • Cẩn thận với equals/hashCode — dùng business key hoặc ID (nhưng ID null khi chưa persist).
  • Không dùng @Builder mà thiếu no-arg constructor — Hibernate cần.
  • Dùng BaseEntity cho audit fields — DRY.
  • Cột có nullable = false cho field bắt buộc.

✅ Best Practices — Quan hệ

  • Luôn LAZY cho mọi quan hệ — override mặc định EAGER của @ManyToOne.
  • Set FK ở owner side — không chỉ thêm vào collection.
  • Cascade chỉ cho quan hệ cha-con thực sự (User-Order là không).
  • Tránh @ManyToMany — tạo entity trung gian.
  • Dùng Set thay List khi cần MultipleBagFetch.

✅ Best Practices — Query

  • DTO Projection khi chỉ cần vài field.
  • JOIN FETCH khi cần load quan hệ.
  • @EntityGraph cho declarative — gọn hơn.
  • @BatchSize khi nhiều collection.
  • 2-query approach khi pagination + JOIN FETCH.
  • Bật SQL log khi dev — phát hiện N+1 sớm.

✅ Best Practices — Transaction

  • @Transactional(readOnly = true) cho query.
  • Transaction ngắn — không gọi external API trong transaction.
  • Không dùng OSIV trong production (Spring Boot 3 khuyến nghị tắt).

❌ Anti-patterns

  • Dùng EAGER cho mọi quan hệ.
  • Expose entity trực tiếp ra API — dùng DTO.
  • OSIV bật trong production — che giấu N+1.
  • Query trong vòng lặp — N+1.
  • Không pagination khi load table lớn.
  • Dùng findAll() rồi filter trong code — phải dùng query.
  • Update entity bằng save() khi đã managed — chỉ cần set field.
